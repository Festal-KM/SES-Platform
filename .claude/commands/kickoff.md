## 1. インタビューの進め方

### 原則

- 🔴 **1 度に投げる質問は最大 4 問**。それ以上並べると回答の質が落ちる。
- 🔴 **ユーザーの回答をそのまま貼らない**。ヒアリング内容を**テンプレートが要求する形式**（表・箇条書き・Mermaid・テスト可能な成功条件）に整形して書く。
- 🔴 **分からないことを推測で埋めない**。特に数値（レート上限・単価・無料枠）は推測せず **§9 未確定事項に回す**。§2 に書いた数値は下流が確定値として扱うため、推測を書くと事故になる。
- ユーザーが「分からない」「任せる」と答えた項目は、**あなたの推奨案を 1 つ提示して確認を取る**。黙って決めない。
- 各ラウンドの冒頭に `Kickoff N/8: <章名>` と進捗を出す。

### ラウンド構成（この順で進める）

`CLAUDE.md` §0 の「埋める順番」に従う。**順番を入れ替えない**（上流が決まらないと下流の質問が意味をなさないため）。

## 2. 各ラウンドの質問

### ラウンド 1: プロダクトの輪郭（§1）

聞くこと：

1. **誰の、どんな業務を、どう変えるプロダクトか**（§1 冒頭の 1 段落）
2. **現状その業務がなぜ回らないのか**（§1.1）— 「面倒だから」で止めず、「どの工程が形骸化し、その結果どうなるか」まで掘る
3. **使う人の区分**（§1.2）— 区分ごとに人数規模・スキル前提・1 日に割ける時間
4. **中核となる業務ループ**（§1.3）— プロダクトが自動化・支援する業務をステージの連なりで

書き方：

- §1.3 は **Mermaid の `flowchart LR`** で書く。ループなら還流先を、一方向フローなら終端を明示する。
- §1.3 の下に「この工程を切ると単なる〈凡庸な既存ツール〉になる」という**中核工程**を必ず 1 つ特定して書く。スコープが揺れたときの判断基準になるため、**ユーザーが答えられない場合は候補を提示して選ばせる**。
- §1.4 は「顧客が使う平面」と「運営者が使う平面」が分かれるかを聞く。単一平面なら**表を消して「本プロダクトは単一平面。」の 1 行**に置き換える。§1.4 で 2 平面と答えたら **§10 は必須**になる。

### ラウンド 2: 技術スタック（§2）

聞くこと：

1. すでに**決まっている**技術（言語・フレームワーク・DB・認証・ホスティング等）
2. リポジトリ構成（モノレポか単一か、ディレクトリと責務、依存方向のルール）

書き方：

- 🔴 **迷っているものは §2 に書かない**。§9 に回す。§2 に書いた瞬間、`tech-selection` は「なぜ採用したか」を後付けで正当化する側に回る。
- 逆に、決まっているのに書かないと下流が別の技術を前提に設計をやり直すことになる。「決まっている / 迷っている」を 1 項目ずつ確認する。
- §2.1 のディレクトリツリーには**必ず責務コメントを付ける**。責務が無いと `programmer` が置き場所を毎回迷う。

### ラウンド 3: ドメインモデル（§4）

聞くこと：

1. 中核となる概念（エンティティ）とその 1 行説明
2. 状態を持つ中核エンティティがあるか。あればその状態遷移の全体

書き方：

- §4.1 は**名前と 1 行説明だけ**。属性・カラムは書かない（`docs/02` と `docs/05` の領分）。
- §4.2 を書く場合は 🔴 **「上図がこのステートマシンの全体である」と明記する**。これが無いと下流ドキュメントが遷移を勝手に足し、状態の意味が発散する。
- 状態設計では以下を必ず確認する（テンプレート §4.2 の記入ガイドに対応）：
  - **失敗と保留を混同していないか** — 「外部要求の前に止まった」と「外部要求の結果失敗した」は別状態にする。混ぜると失敗率の指標が汚れて監視が誤検知する
  - **片道の遷移はどれか**
  - **人間の操作に限る遷移（自動リトライ禁止）はどれか**
  - **不正遷移のエラー型**（例: `InvalidStateTransitionError` / HTTP 422）

### ラウンド 4: スコープ（§5 §6）

聞くこと：

1. Phase 0〜4 の内容
2. **やらないこととその理由**

書き方：

- 🔴 §5 の成功条件は**テスト可能な文**で書く。「基盤ができている」は不可。「空のダッシュボードにログインでき、分離が効いていることをテストで証明できる」のように書く。`pm` の完了確認モードがこれを判定基準に使うため、曖昧だと判定できない。
- 自分でコントロールできない外部依存（審査・契約・アカウント開設）があるか聞き、あれば **Phase 1 のクリティカルパスに置かない旨**を §5 末尾に書く。
- 🔴 §6 は**理由を必ず添える**。理由の無い「やらない」は、下流エージェントが「良かれと思って」実装してくる。

### ラウンド 5: ハードルール（§3）— **最重要**

🔴 **このラウンドに最も時間をかける。§3 の質がこのハーネス全体の精度を決める。**

手順：

1. まず `recipes/` を Glob して、利用可能なレシピの一覧を得る。
2. ラウンド 1〜4 の回答から、**該当しそうなレシピを推定して提示**する：

   | 聞くこと | 該当したら |
   |---|---|
   | 複数の顧客組織のデータを 1 つの DB に入れるか | `recipes/multi-tenant-rls.md` |
   | 取り消せない外部書き込み（投稿・送信・決済）があるか | `recipes/idempotent-external-writes.md` |
   | LLM を使うか | `recipes/ai-layer.md` |
   | 生成物や投入物に審査・承認が要るか | `recipes/approval-gate.md` |
   | SaaS として運営者が顧客を管理するか | `recipes/operator-console.md` |
   | 営業デモ環境が要るか | `recipes/demo-environment.md` |

3. 該当するレシピを読み、**プロダクトの語彙に置き換えて §3 に貼る**。レシピをそのままコピーしない（プレースホルダが残る）。
4. レシピに無いプロダクト固有のルールを追加でヒアリングする。

🔴 **書いたハードルール 1 件ごとに、以下 4 条件を満たしているか自己検査する**（`CLAUDE.md` §0 の基準）：

1. **違反が一意に判定できるか** — 「適切に検証する」は不可。「〈特定のアクセサ〉を経由しない DB アクセスを書かない」なら可
2. **破れない担保まで書いてあるか** — 「気をつける」は不可。「Lint で禁止する」「DB の `UNIQUE` 制約で担保する」なら可
3. **なぜそれが事故なのかが 1 行あるか** — 理由が無いとエージェントは機械的に拡大解釈する
4. **例外を作った場合、射程を明示して「ここだけ」と書いてあるか** — 例外が 1 つあると、エージェントは類似ケースにも例外を作りたがる

条件を満たさない項目は、**ユーザーに追加質問して満たすまで書き直す**。ここで妥協すると `design-reviewer` と `code-reviewer` が判定できず、ハーネス全体が「それっぽいレビュー」に劣化する。

該当しないカテゴリ（§3.1〜§3.4）は**カテゴリごと削除してよい**（§3 はサブセクション番号を他章から参照されていないため）。ただし §3.5 は残す。

### ラウンド 6: KPI と未確定事項（§7 §9）

聞くこと：

1. 成否を測る指標
2. **絶対に起こしてはならない事故**
3. 確度が低く裏取りが必要な項目

書き方：

- 🔴 §7 は「0 件」「N% 以上」など**判定可能な形**で書く。特に事故指標は `**0 件**（許容しない）` と書く。この 1 行が `code-reviewer` の厳しさを決める。
- §9 には「何を確認すべきか / なぜ重要か」をセットで書く。`tech-selection` がこれを公式ドキュメントで裏取りする。
- ラウンド 2 で「迷っている」と言われた技術は、**すべて §9 に落ちていることを確認する**。

### ラウンド 7: オプション章の要否（§10〜§13）

各章について「該当するか」を聞き、判定する：

| 章 | 該当条件 |
|---|---|
| §10 管理平面 | SaaS で運営者が顧客テナントを管理する。**§1.4 が 2 平面なら必須** |
| §11 環境構成 | 本番・開発以外の環境（営業デモ / ステージング）が要る |
| §12 AI 運用ロール | プロダクト内部で LLM に複数の役割を担わせる |
| §13 マルチデバイス | モバイル / タブレットでの利用がある |

🔴 **該当しない章は、章そのものを削除せず、見出しを残して 1 行だけ書く**：

```markdown
## 12. AI 運用ロール（ハーネス設計）

本プロジェクトでは該当なし。
```

**理由**: `.claude/agents/*.md` は `CLAUDE.md` の章番号 (§1〜§13) を参照する契約で書かれている。章を消して番号を詰めると、全エージェントの参照がずれる。`design-reviewer` は章が丸ごと消えていたら `## ESCALATE` を返す仕様になっている。

該当する章は、対応するレシピ（§10 → `recipes/operator-console.md`、§11 → `recipes/demo-environment.md`、§12 → `recipes/ai-layer.md`）を読んでから埋める。

### ラウンド 8: 仕上げ・検証

1. **§0 章を削除する**（「記入後に削除してよい」と書かれている章）。
2. **すべての `> 📝 **記入ガイド**:` 行を削除する**。
3. **すべての `<!-- OPTIONAL -->` コメントを削除する**。
4. 検証を機械的に行う：

   ```bash
   grep -n "{{" CLAUDE.md          # 0 件であること
   grep -n "📝" CLAUDE.md          # 0 件であること
   grep -n "OPTIONAL" CLAUDE.md    # 0 件であること
   grep -n "^## " CLAUDE.md        # §1〜§13 が抜けなく並んでいること
   ```

5. 章番号が §1〜§13 まで欠番なく存在することを確認する。**§8 は原則そのまま残す**（エージェントを増減した場合のみ §8.1 の表を直す）。

## 3. 書き込みの作法（重要）

🔴 **`CLAUDE.md` 全体を 1 回の `Write` で書き直そうとしない。** 出力トークン上限に当たってツール呼び出しが失敗し、**ファイルごと失われる**。

手順：

1. 各ラウンドの結果は、**そのラウンドが対象とする章だけ**を `Edit` で置換する。
2. 1 回の `Edit` は **300 行以内**に収める。超えるなら章内でさらに分割する。
3. 各ラウンド終了時に `wc -l CLAUDE.md` で行数を確認し、意図せず縮んでいないかを見る。
4. ラウンド 8 の削除作業も同様に、`Edit` を複数回に分けて行う。

## Rules

- 🔴 **推測でプレースホルダを埋めない**。特に外部 API の数値は §9 に回す。
- 🔴 **章番号を詰めない**。該当なしの章は見出し + 1 行を残す。
- 🔴 **`{{...}}` を 1 つでも残したまま `## KICKOFF_COMPLETE` を出さない**。`pm` の完了確認モードは未置換プレースホルダを無条件 NG として扱う。
- **§8 を書き換えない**。エージェント運用マニュアルはハーネスの仕様であり、プロダクト固有情報ではない。
- **ユーザーの回答を要約しすぎない**。特に §1.1（課題）と §3（ハードルール）は、具体性が失われると下流が薄くなる。
- **設計ドキュメント (`docs/01`〜) をこのコマンドで書き始めない**。`/kickoff` の責務は `CLAUDE.md` のみ。

最後の行は必ず `## KICKOFF_COMPLETE` または `## KICKOFF_INCOMPLETE: <残っている章>` のいずれか。
