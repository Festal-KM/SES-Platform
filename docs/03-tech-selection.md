## 1. 選定方針

### 1.1 判断軸（優先順）

本プロダクトの技術選定は、次の順で判断する。上位の軸が下位の軸に優先する。

| # | 判断軸 | なぜこの順位か | 具体的な適用 |
|---|---|---|---|
| **1** | **事故ゼロの担保が「設計で不可能」になること** | `CLAUDE.md` §7 の 7 つの「0 件（許容しない）」は他のどの価値とも交換しない（`docs/01` 章 3.3）。**「気をつける」で担保する技術を選ばない** | RLS を持つ DB（PostgreSQL）、DB の `UNIQUE` 制約で冪等性を担保できる構成、静的検査で禁止経路を塞げる言語（TypeScript + ESLint） |
| **2** | **コストの予測可能性** | AI・メール・電子署名の従量原価を抱えたまま席課金で売る構造であり（`CLAUDE.md` §10.2）、**単価が読めない依存は逆ざやの温床**になる。§7 の損益分岐はこの軸の出力である | 単価が公開されている外部 API のみを選ぶ。単価非公開（要問い合わせ）のサービスは、代替が無い場合を除き採らない |
| **3** | **運用負荷の低さ** | 運営者は「少数」（`docs/02` A-10。`Q-12` 未確定）。**自前運用するコンポーネントを増やすと、その分だけ運営平面の監視項目が増える** | マネージドを既定とし、セルフホストは「マネージドだと要件を満たせない」場合に限る |
| **4** | **型安全と単一経路の強制** | `CLAUDE.md` §3.1 / §3.2 は「唯一の経路」を要求する。**経路が 1 つであることをコンパイル時・静的検査時に証明できる**ことが、レビューの負荷を決める | TypeScript `strict`、Zod による境界検証、ESLint `no-restricted-imports` |
| **5** | **既存決定との整合** | `CLAUDE.md` §2 が確定事項である以上、それと噛み合わない技術は、単体で優れていても採らない | Prisma と共存できる RLS 実装、Vercel と共存できるワーカー基盤 |

### 1.2 この方針から導かれる、採らない選択

| 採らないもの | 理由 |
|---|---|
| **アプリ層のフィルタだけでテナント分離を担保する構成** | 判断軸 1。`CLAUDE.md` §3.1 が「RLS と Prisma 拡張の二重防御」を要求している。片方が静かに無効化されたときに止まらない構成は選定対象に入らない |
| **単価が要問い合わせの外部 API を Phase 1〜2 の必須依存に置くこと** | 判断軸 2。§7 の損益分岐が算出できず、`Q-15`（プラン別クォータ）が決まらない |
| **セルフホストの検索エンジン（Elasticsearch / OpenSearch）を Phase 1 から入れること** | 判断軸 3。PostgreSQL で目標性能を満たせるかを先に検証する（§3.7）。満たせないと分かってから入れる |
| **複数 LLM プロバイダの抽象化レイヤ** | `CLAUDE.md` §6 / §3.2 が明示的に対象外。切替可能性のために統制（記録・PII 除去・原価把握）を緩めない |
| **「未設定ならモックにフォールバック」する外部連携の実装** | `CLAUDE.md` §11.1 / `docs/02` NFR-ENV-3。**成功したように見えて実際には送信されていない**という壊れ方を生む |

### 1.3 本書が扱う「確度」の表記

裏取りの結果は、次の 3 段階で確度を明示する。**確度を偽らない。**

| 表記 | 意味 |
|---|---|
| **一次情報** | 提供元の公式ドキュメント / 公式価格ページで確認した。出典 URL を併記する |
| **二次情報のみ・要再確認** | 公式ドメインで該当の記述に到達できず、第三者の記事等でしか確認できなかった。**設計の前提にしてよいが、契約前に必ず一次情報で再確認する** |
| **未確認** | 確認できなかった。**この値を前提にした設計をしてはならない。** 誰が・いつ・何をもって確定させるかを併記する |

### 2.2 `CLAUDE.md` §2 の確定事項に対する既知の懸念（ESCALATE には至らないもの）

| # | 懸念 | 影響 | 本書での扱い |
|---|---|---|---|
| 1 | **Prisma + RLS の併用は、コネクションプーリング（PgBouncer 等）の transaction モードと相性が悪い経路がある** | `SET LOCAL app.tenant_id` がトランザクション外で発行されると、**別テナントのリクエストに設定が漏れる**。`CLAUDE.md` §7 の「テナント越境 0 件」に直撃する | §4.3 で「必ず `$transaction` 内で `SET LOCAL` を発行し、その中でのみクエリする」構造と、それを静的検査で強制する方式を定義した。**§2 の変更は不要** |
| 2 | **Vercel のサーバレス実行環境では、BullMQ のワーカーを常駐させられない** | `CLAUDE.md` §2 は「Vercel（Web）+ コンテナ基盤（ワーカー）」と既に分離しており、**矛盾しない**。ただし Web 側から Redis へ接続する際のコネクション枯渇が起きうる | §4.15 でワーカー基盤とコネクション方式を定義した。**§2 の変更は不要** |
| 3 | **Auth.js は 2FA（TOTP）を標準機能として持たない** | `CLAUDE.md` §3.5 の「運営者と `OWNER` / `ADMIN` は 2FA 必須」が、追加実装なしでは満たせない | §4.9 で TOTP の実装方式を追加選定した。**§2 の変更は不要**（Auth.js は認証基盤としての役割を果たし、2FA は上乗せで実現できる） |
| 4 | **`CLAUDE.md` §2 のモデル既定 `claude-sonnet-5` は 2026-09-01 に値上げ予定と告知されていた** | AI 原価の前提が変わる | 🔴 **裏取りの結果、値上げは行われないことが公式に告知された**（§3.3）。**$2 / $10 per MTok が標準価格として据え置き**。§7 の試算はこの確定値を用いる |

### 3.1 🔴 電子署名サービス（`CLAUDE.md` §9-2 / `Q-2` / `BR-51` / `F-049` / `R-6`）

#### 3.1.1 決定的な問い: 契約書の送信元名義をテナントごとに分けられるか

**結論: 「運営者が 1 つの ISV アカウントを持ち、全テナントの契約書をそこから送る」方式では分けられない。** 主要サービスのうち一次情報で確認できた DocuSign は、この点を明文で否定している。

| 事実 | 出典 |
|---|---|
| **エンベロープの `sender` プロパティは read-only であり、作成リクエストで指定した値は無視される** | [Docusign Developers Blog — ISV Embedded Signing Update: Change the Sender's Address](https://www.docusign.com/blog/developers/isv-embedded-signing-update-change-the-senders-address) |
| **顧客のメールアドレスでユーザーを作って送る運用は "strongly discouraged"。ISV ライセンス上、顧客が ISV のパートナーアカウントにユーザーメンバーシップを持つべきではない** | 同上 |
| **現時点の回避策は 2 つのみ**: ①システムユーザーのメールアドレスに顧客名を含める（例 `acme@vendor.com`。**ドメインは ISV のもの**）②`emailSettings` の `replyEmailAddressOverride` / `replyEmailNameOverride` で**返信先だけ**を顧客のものに上書きする | 同上 |
| Adobe Acrobat Sign では、**複数組織のアカウントへアクセスする PARTNER ドメインのアプリは、Adobe の認定（certification）プロセスを経る必要がある** | [Adobe Acrobat Sign — Partner Application Quickstart](https://opensource.adobe.com/acrobat-sign/embedpartner/gstarted.html)（**二次情報のみ・要再確認**: 認定の所要期間は公開情報に無い） |

🔴 **これは `docs/01` `R-6` / `BR-51` / `Q-2` の懸念がそのまま現実である**ことを意味する。ISV 一括方式を採ると、**取引先には `no-reply@<運営者ドメイン>` から契約書が届き、差出人名も運営者名義になる**。SES の商流では、契約書の差出人が取引の当事者でない第三者であることは受け入れられない可能性が高い。

#### 3.1.2 したがって採る方式: **テナントが自社の電子署名契約を接続する（BYO 接続）**

| 観点 | 内容 |
|---|---|
| **方式** | テナント（契約 SES 企業）が**自社名義で電子署名サービスと契約**し、その API 資格情報を本プロダクトに接続する。本プロダクトは**そのテナントのアカウントの代理として**書類を作成・送信する |
| **送信元名義** | **テナント自身になる。** 運営者名義の問題が構造的に発生しない（`BR-51` を満たす） |
| **成立の根拠（クラウドサイン）** | Web API は**アカウントの管理画面「Web API 設定」から有効化**する。資格情報はそのアカウント（＝テナントの契約）に属する。API 実行ユーザーは書類関係者に含まれる。[クラウドサイン Web API 利用ガイド](https://help.cloudsign.jp/ja/articles/2681259) |
| **成立の根拠（GMO サイン）** | Web API 連携は**スタンダードプラン以上**の契約で利用可能。資格情報は同様にそのアカウントに属する。（**二次情報のみ・要再確認**: [GMO サイン 料金プラン](https://www.gmosign.com/price/) は公式だが、API の資格情報の帰属について公式ドキュメントの明文に到達できなかった） |
| **成立の根拠（DocuSign）** | Authorization Code Grant により、**顧客が自分の DocuSign アカウントで本プロダクトを認可する**（`consent` 経由）。この場合の送信者は顧客アカウントのユーザーであり、ISV アカウントからの送信ではない。（**未確認**: トークン有効期間の具体値は公式ページの本文を取得できなかった。§3.1.6 参照） |
| **副次的な利点** | **送信 1 通あたりの原価がテナント持ちになる。** `docs/02` 章 7.5 の原価定義から「④電子署名（リクエスト数 × 単価）」が消えるため、§7 の逆ざやリスクが 1 項目減る |
| **副次的な欠点** | **テナントが電子署名サービスと未契約だと `F-049` が使えない。** Phase 3 の機能であり、`F-047`（契約管理）と `F-048`（テンプレート差し込み）は電子署名なしでも成立するため、**「電子署名は接続したテナントのみのオプション機能」として設計する** |

🔴 **`F-049` の設計上の帰結（`docs/05` へ）**: 電子署名は**テナント単位の接続（`TenantEsignConnection`）を前提とし、未接続テナントでは `Contract` が `DRAFT` → `SENDING` に遷移できない**。`docs/02` 章 5.5 の状態機械は変更しない（遷移が起きないだけ）。

#### 3.1.4 冪等性の仕組み（`CLAUDE.md` §3.4 / `docs/02` 章 7.8）

🔴 **クラウドサインの Web API に、冪等性キー（Idempotency-Key 相当）の仕組みは公式ドキュメントで確認できなかった（未確認 = 無いものとして設計する）。**

**したがって `CLAUDE.md` §3.4 が想定するとおり、アプリ側の DB 制約が唯一の防御線である。** 設計は次を満たすこと（`docs/05` 申し送り 3）:

| # | 担保 | 実装 |
|---|---|---|
| 1 | **1 契約につき外部 API 呼び出しは高々 1 回** | `Contract` を `DRAFT` → `SENDING` へ **CAS 更新**（`UPDATE ... WHERE id = ? AND status = 'DRAFT'` の更新件数 1 を条件に進む）。更新できなかった実行は外部 API を呼ばずに終了する |
| 2 | **`idempotency_key` の一意性を DB が保証する** | `ContractSendAttempt(contract_id, idempotency_key)` に `UNIQUE(contract_id, idempotency_key)`。キーは `contract_id` + `contract_version` から**決定的に導出**する（乱数にすると再実行のたびに別キーになり意味を失う） |
| 3 | **外部 API の応答が確定した後にリトライしない** | BullMQ のキュー定義で送信系は `attempts: 1`, `backoff: undefined`。キュー生成を `packages/connectors` の 1 箇所に閉じ、**`attempts > 1` を送信系キューに設定できない型**にする |
| 4 | **応答不明（タイムアウト）は `SEND_FAILED` に確定** | `docs/02` 章 7.8「応答不明時の運用」。自動再送しない。人間が実際の到達を確認して `F-049` から再送（`F-049 AC-3` の確認表示を伴う） |
| 5 | **外部で書類が既に作られていないかを、再送前に照会できる** | 再送時に、保存済みの外部書類 ID があれば**先に書類の状態を GET で照会**し、既に存在すれば送信せず状態同期に切り替える（多重作成の最後の砦） |

#### 3.1.5 Webhook の仕様（クラウドサイン。一次情報）

| 項目 | 内容 | 出典 |
|---|---|---|
| **通知イベント** | ①書類の締結完了時 ②書類の取り消し・却下時 ③メール不達時（確認依頼メール / 書類転送メール / 締結完了メール） | [Webhook 機能](https://help.cloudsign.jp/ja/articles/417935) |
| **ペイロード** | JSON。`documentID` / `status` / `userID` / `email` / `text` | 同上 |
| **設定数の上限** | **最大 20 個** | 同上 |
| **再送の条件と回数** | HTTP **500 番台**を返した場合のみ「送信失敗」として扱い、**10 分間隔で最大 3 回まで自動再送**。**400 番台は現行仕様では成功扱いで再送されない** | [Webhook 実行時の挙動](https://help.cloudsign.jp/ja/articles/9977727) |
| **レスポンスの扱い** | 2024 年 12 月時点でステータスコードを参照していないが、**将来参照する実装に切り替える可能性があるため 200–299 を返すことが推奨されている** | 同上 |
| **署名検証** | 🔴 **公式ドキュメントに署名検証の記載が無い（未確認 = 無いものとして設計する）** | 同上 |

🔴 **署名検証が無いことの設計上の帰結（`docs/05` へ）**:

1. **Webhook の受信 URL に、テナントごとの推測不能なシークレットをパスに含める**（例 `/api/webhooks/esign/{tenant_id}/{opaque_secret}`）。シークレットは `TOKEN_ENCRYPTION_KEY` で暗号化して保存する（§4.4）。
2. 🔴 **Webhook のペイロードを信頼して状態を確定させない。** 受信は「照会のトリガー」としてのみ扱い、**必ず API で書類の状態を GET し直してから `Contract` の状態を遷移させる**（`docs/02` 章 7.8「外部応答の正規化」）。
3. **再送による重複配信を前提に、受信処理を冪等にする**。`WebhookDelivery(provider, external_document_id, status, received_at)` に `UNIQUE(provider, external_document_id, status)` を置き、同じ状態遷移を 2 回適用しない。
4. **400 番台が成功扱いで再送されない**ため、**受信側のバリデーションエラーで 4xx を返すと通知が永久に失われる**。受信エンドポイントは「受け取って即座に 200 を返し、処理はジョブに積む」構造にする。処理失敗はこちらの監視（`F-059`）で拾う。

### 3.2 🔴 メール送信基盤（`CLAUDE.md` §9-3 / `docs/02` 申し送り 2・8 / `F-002` / `F-022` / `F-039` / `F-041`）

#### 3.2.1 選定: **Amazon SES**

#### 3.2.7 テナント独自ドメイン送信の設計（本書の判断）

| 段階 | 送信元 | 適用フェーズ |
|---|---|---|
| **既定（フォールバック）** | 運営者が管理する**プラットフォーム共通ドメイン**（例 `notifications@<platform>.jp`）。`Reply-To` にテナントの担当者アドレスを設定する | Phase 0〜 |

🔴 **`CLAUDE.md` §9-3 の「取引先へのメールが運営者ドメインから飛ぶ設計は避けたい」への回答**: **回避できる。ただしテナントの DNS 作業を伴うため、既定は共通ドメイン + `Reply-To` とし、独自ドメインは opt-in とする。** 提案メール（`F-022`）と面談調整（`F-041`）は取引先に届くため、**独自ドメイン未設定のテナントに対しては、設定を促す表示を `F-022` の送信画面に出す**（`docs/04` へ）。

#### 3.2.8 `sandbox` 環境での二重防御（🔴 `docs/02` 申し送り 8 への回答）

`docs/02` 章 7.6 の判定表は**アプリ層で宛先を分類**するが、**それだけに頼らない構成を組める。**

| 層 | 担保 | 破れたときに何が起きるか |
|---|---|---|
| **第 1 層（アプリ）** | メール送信の単一経路が「宛先の分類」を必須入力に取る。分類 2 / 3 / 4 は `sandbox` でモックコネクタに振る（`docs/05` 申し送り 10） | 分類のバグで実送信側に落ちる |
| 🔴 **第 2 層（基盤）** | **`sandbox` 環境は、本番とは別の AWS アカウント（かつ SES サンドボックス状態のまま）を使う。** サンドボックス中は**検証済み宛先にしか送れない**ため、ホスト所属利用者のアドレスだけを identity として検証しておけば、**分類 2 / 3 / 4 宛の送信は SES 側で必ず失敗する** | 検証済み identity を増やしすぎると防御が緩む。**identity の追加を IAM ポリシーで運営者の手動操作に限定する** |
| 🔴 **第 3 層（環境変数）** | `packages/config` の Zod スキーマで、**`APP_ENV !== 'production'` のときに本番の `AWS_ACCESS_KEY_ID` / SES 設定が入っていたら起動を失敗させる**（NFR-ENV-4）。SES のアカウント ID を環境変数に持ち、環境ごとに固定値と一致するかを検証する | — |

⚠️ **第 2 層の制約**: `sandbox` は 24 時間で **200 通 / 秒間 1 通**の上限を持つ。見込み客が複数社同時に試す場合に不足しうる。**`docs/02` の `sandbox` は「見込み客が自分の実データで試す」環境であり、送信するのはホスト所属利用者宛のアカウント運用メールに限られる**（分類 1）ため、200 通 / 日で足りる見込み。**不足した場合は「サンドボックス状態のまま送信クォータだけ引き上げる」申請ができるかを確認する必要がある（未確認）。** 担当: 人間。期限: `sandbox` 環境の構築時。

#### 3.3.3 構造化出力の対応方式（🔴 `CLAUDE.md` §3.2 への回答。一次情報）

`CLAUDE.md` §3.2 は「Zod スキーマ + 構造化出力（tool use）」を要求している。**現行 API では、より直接的な手段が 2 つある。**

| 方式 | 指定 | 用途 | 本書の方針 |
|---|---|---|---|
| **JSON Outputs** | `output_config: { format: { type: "json_schema", schema: {...} } }` | **応答そのものを JSON スキーマに強制する** | 🔴 **6 ロールすべてでこれを既定にする。** `docs/02` 章 8.1 の出力スキーマは全ロールが「単一の構造化オブジェクト」であり、ツール呼び出しの形を取る必要が無い |
| **Strict Tool Use** | `tools: [{ name, strict: true, input_schema }]` | ツール入力のスキーマ適合を保証する | 使わない。本プロダクトに LLM から呼ぶツールは無い（`CLAUDE.md` §12.3「ロールは自律エージェントではない」） |

**TypeScript SDK の Zod ヘルパー**（一次情報）:

```ts
import { zodOutputFormat } from "@anthropic-ai/sdk/helpers/zod";
const response = await client.messages.parse({
  output_config: { format: zodOutputFormat(schema) },
  // ...
});
```

🔴 **`packages/ai` は、Zod スキーマから `zodOutputFormat` を経由する経路を唯一の出力定義経路とする。** アプリコードが生の `output_config` を組み立てる経路を作らない（`CLAUDE.md` §3.2）。

**JSON Schema のサポート範囲と制約**（[出典](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)）:

| 区分 | 内容 | 本プロダクトへの影響 |
|---|---|---|
| **対応** | `object` / `array` / `string` / `integer` / `number` / `boolean` / `null`、`enum`（スカラーのみ）、`const`、`anyOf`、`allOf`、`$ref` / `$def`（内部）、文字列フォーマット（`date-time` / `date` / `email` / `uri` / `uuid` 等）、`minItems`（0 または 1 のみ）、`additionalProperties: false` | `docs/02` 章 8.1 の 6 スキーマはすべて表現できる |
| 🔴 **非対応** | **再帰的スキーマ**、enum 内の複雑型、外部 `$ref`、**`minimum` / `maximum` / `minLength` / `maxLength` などの数値・長さ制約**、`additionalProperties: false` 以外の値 | 🔴 **`sheet-parser` の「経験年数」に `min: 0, max: 60` のような制約をスキーマ側で掛けられない。** **Zod 側の `.refine()` / `.min()` は API に渡らないため、受信後の `parse` で必ず再検証する**（§4.1） |
| **スキーマのキャッシュ** | 初回リクエストはスキーマコンパイルの分だけ遅延する。**同一スキーマは 24 時間自動キャッシュ**される。スキーマ構造を変えると無効化される | 🔴 **プロンプト版を上げるたびにスキーマを変えると、初回レイテンシが毎回発生する。** `docs/02` 章 7.1 のジョブ許容待ち時間（抽出 3 分）には十分収まるが、`F-020`（ゲート 30 秒）は注意が要る |

**失敗時の挙動**: `docs/02` 章 8.7 のとおり。**スキーマ違反の応答は破棄し、自由文を正規表現でパースして救わない。** 同一プロンプトで最大 2 回まで再試行し、なお失敗したらロールの失敗として扱う。**再試行分も `AiUsage` に記録して原価に計上する**（`F-026 AC-1`）。

#### 3.4.2 競合との比較

| 観点 | **GuardDuty Malware Protection for S3** | ClamAV セルフホスト（ワーカーにサイドカー） | Cloudmersive / VirusTotal 等の SaaS |

| # | 内容 |

| 1 | 🔴 **保護バケット数の上限は 25（アカウント × リージョン）。テナントごとにバケットを分ける設計を採らない。** 1 バケットにテナント別プレフィックス（`t/{tenant_id}/...`）で格納し、バケット全体を保護対象にする。テナント分離は**プレフィックス + 署名付き URL の発行制御 + IAM 条件**で担保する（§4.4） |

| 6 | **`development` / CI では ClamAV（`clamd`）のコンテナを使う。** `packages/connectors` の `MalwareScanner` インタフェース（`enqueue` / `getResult`）で差し替える（`CLAUDE.md` §11.1 の「起動時 1 箇所の DI」） |

### 3.5 スキルシート解析（`CLAUDE.md` §9-5 / `Q-6` / `F-032` / `docs/02` 申し送り 5）

#### 3.5.1 対象形式ごとの抽出方式

🔴 **`CLAUDE.md` §3.2 は「スキルシートの原本を無加工で LLM に送らない」を要求する。したがって「ファイルをそのまま Claude に渡す」経路は、マスキングを挟めない形式では採れない。** これが方式選定の第一制約である。

| 形式 | 抽出方式 | マスキングの位置 | 採否 |
|---|---|---|---|
| **xlsx** | **`exceljs` でセル値・シート構造をテキスト化** → `packages/ai` の入口で PII マスキング → テキストのみ Claude へ | 🔴 **テキスト化の後、LLM 呼び出しの前**（決定的に実行できる） | 🔴 **Phase 2 の主対象。** SES のスキルシートは xlsx が大多数 |
| **docx** | **`mammoth` で本文テキスト + 表を抽出** → 同上 | 同上 | 🔴 **Phase 2 の対象** |
| **pdf（テキスト層あり）** | **`pdfjs-dist` でテキスト層を抽出** → 同上 | 同上 | 🔴 **Phase 2 の対象。既定はこちら** |
| **pdf（テキスト層なし＝スキャン画像）** | Claude の `document` ブロック（PDF は各ページを**テキスト + 画像**として処理される） | ⚠️ **画像に写った氏名・顔写真をテキストマスキングでは消せない** | 🔴 **Phase 2 の対象外。`Q-6` の回答として「画像 PDF は非対応」とする**（§3.5.3） |
| **画像（jpg / png）のスキャン** | 同上 | 同上 | 🔴 **対象外。Phase 4 で再評価** |

**PDF の仕様（一次情報）**: 最大リクエストサイズ 32 MB、**最大 600 ページ**（コンテキストが 1M 未満なら 100 ページ）、パスワード・暗号化なしの標準 PDF。**各ページは画像に変換され、抽出テキストと併せて渡される**。トークンは**テキストで 1 ページ 1,500〜3,000 tok**＋画像トークン。[出典](https://platform.claude.com/docs/en/build-with-claude/pdf-support)

#### 3.5.2 🔴 `Q-6` への回答（対象範囲と精度目標）

| 論点 | 本書の結論 | 根拠 |
|---|---|---|
| **対象形式** | 🔴 **xlsx / docx / テキスト層のある pdf の 3 形式。画像 PDF と画像ファイルの OCR は Phase 2 の対象外とし、Phase 4 で再評価する** | ①`CLAUDE.md` §3.2 の PII マスキングを、画像に対して確実に実行する手段が無い（顔写真・氏名が画像に焼き込まれている）。②`CLAUDE.md` §7 の「PII 未マスキングでの LLM 送信 0 件」は**画像を送った時点で担保できない** |

#### 3.5.3 「Claude のドキュメント読み取り機能で足りるか」への回答

**足りない。理由は精度ではなく統制である。**

Claude の PDF サポートは技術的には xlsx を除く多くの文書を読めるが、**ファイルをそのまま渡すと `CLAUDE.md` §3.2 のマスキングを挟む場所が無くなる**。マスキングは「LLM に送る前に決定的に実行する」ことが要件であり（`CLAUDE.md` §7「0 件（許容しない）」）、**モデルに「氏名を無視して」と指示することは統制ではない**（プロンプトインジェクションで破られる。`docs/02` 章 7.3）。

#### 3.8.2 メータリングの実装方式（一次情報）

| 項目 | 内容 | 出典 |
|---|---|---|
| **API** | `POST /v1/billing/meter_events`。`event_name`（必須、100 文字以内）/ `payload`（必須。`stripe_customer_id` と `value`）/ `identifier`（任意）/ `timestamp`（任意） | [Create a billing meter event](https://docs.stripe.com/api/billing/meter-event/create) |
| 🔴 **冪等性** | **`identifier` による重複排除。ただし「少なくとも 24 時間のローリング期間内での一意性」しか保証されない。** ドキュメントは「偶発的なリトライなど、極めて短い時間間隔で起きる問題への対処が主目的」と明記している | 同上 |

🔴 **本書の判断: Phase 3 では Billing Meters を採る。Metronome は採らない。**

| 理由 | 内容 |
|---|---|
| 1 | **本プロダクトのメータリング粒度は月次 1 回で足りる。** クォータ超過分は**月末に 1 テナント 1 イベント**送れば済む（`docs/02` 章 7.5 の「クォータ消化率」はアプリ側で日次集計している）。Metronome が解く「1 秒/1 日あたり大量のイベント」という問題を本プロダクトは持たない |
| 2 | **依存を 1 つ増やさない**（判断軸 3）。Metronome は Stripe とは別の課金基盤であり、運営平面の監視対象が増える |
| 3 | **`docs/02` 章 7.5 は「自社の `UsageCounter` が原価と消化率の正である」構造になっている。** 課金基盤にリアルタイムの利用量可視化を求めていない |

| **WebSocket** | **2026-06-22 に Public Beta で提供開始。** Fluid compute 上で動作し、他の関数呼び出しと**同じ制限と料金体系**に従う。**Active CPU 課金のため、アイドル接続時間には課金されない** | [WebSocket support is now in Public Beta](https://vercel.com/changelog/websocket-support-is-now-in-public-beta) |
| **リクエスト / レスポンスボディ上限** | **4.5 MB** | [Vercel Functions Limits](https://vercel.com/docs/functions/limitations) |
| **ファイルディスクリプタ** | **1,024（同時実行間で共有）**。DB 接続・HTTP 接続を含む | 同上 |

#### 3.9.3 結論: **Phase 2 は SSE を主、ポーリングをフォールバックとする**

| 選択肢 | 評価 | 判定 |
|---|---|---|
| **ポーリング（5〜10 秒間隔）** | 7,000 セッション × 10 秒間隔 = **700 req/s** が常時。Vercel の関数呼び出し課金と DB 負荷が無駄に高い。**チャットの体感も悪い** | **主方式にはしない。SSE が使えない環境のフォールバックとしてのみ使う（間隔 15 秒）** |
| 🔴 **SSE（Server-Sent Events）** | ①**単方向で足りる**（送信は通常の POST。双方向が不要）②Vercel の Fluid compute で成立し、**接続 1 本あたり最大 800 秒**（それを超えたらクライアントが自動再接続する。SSE は再接続が標準仕様）③**Active CPU 課金のため、アイドル接続のコストが低い**④ロードバランサ・プロキシとの相性が WebSocket より良い | 🔴 **採用** |
| **WebSocket** | Public Beta（2026-06〜）。双方向が要る要件が無い。**ベータ機能を `CLAUDE.md` §7 の事故ゼロ要件を負う経路に置かない** | **採らない。Phase 4 で再評価** |
| **外部のリアルタイム基盤**（Pusher / Ably / Supabase Realtime） | 依存が 1 つ増え、**チャット本文が第三者を経由する**。`CLAUDE.md` §10.5 は運営者にすらチャット本文を見せないと定めており、**第三者経由は方針と噛み合わない** | **採らない** |

#### 3.9.4 🔴 SSE の配置（重要）

**SSE のエンドポイントを `apps/web`（Vercel）に置くか、ワーカー基盤側に置くかを分ける。**

| 段階 | 配置 | 根拠 |
|---|---|---|
| **Phase 2（初期）** | **`apps/web` の Route Handler に置く**（Vercel）。イベントは Redis の Pub/Sub で受けて SSE に流す | 実装が単純。**同時接続が数百規模なら十分** |
| **Phase 3 以降（同時接続が 1,000 を超えたら）** | 🔴 **SSE 専用のプロセスをワーカー基盤側（コンテナ）に分離し、`/realtime/*` をそこにルーティングする** | ①Vercel の**ファイルディスクリプタ上限 1,024（同時実行間で共有）**が、長時間保持される SSE 接続 + DB/Redis 接続で圧迫される ②800 秒ごとの再接続が 7,000 セッション分発生すると、再接続の集中（thundering herd）が起きる ③常駐プロセスなら接続を安価に保持できる |
| **判断の基準** | 🔴 **「1 リージョンあたりの同時 SSE 接続数が 1,000 を超えたら分離する」を運用の閾値とする。** 運営平面（`F-059`）に同時接続数のメトリクスを出す | 誰が: `pm` が Phase 3 の計画時に判断。何をもって: 上記メトリクスの実測値 |

#### 3.9.5 設計上の帰結（`docs/05` へ）

| # | 内容 |
|---|---|
| 1 | 🔴 **SSE の接続時にも、二重境界（`tenant_id` + `partner_company_id` + `ThreadParticipant`）の認可を必ず通す。** 「接続時に 1 回だけ認可して、以後は流しっぱなし」にしない。**参加会社から外れた時点でストリームを切る**（`CLAUDE.md` §3.1 経路 3） |

### 4.2 PII マスキング（LLM 入力）

| 項目 | 内容 |
|---|---|
| **対応機能** | `F-032`（`AC-1`）/ `F-034` / `F-031` / `F-044`。`BR-11` / `BR-12` |

| **方式** | ①**既知値の置換**（主）— `Engineer` レコードが持つ氏名・生年月日・電話・メール・現所属会社名を DB から取得し、**テキスト中のその文字列を `[名前]` `[生年月日]` 等のプレースホルダに置換**する。②**パターン検出**（補助）— メールアドレス・電話番号・郵便番号・マイナンバー形式・生年月日形式の正規表現で残存を検出し、**検出したら置換したうえで `AiUsage` に「パターン検出による追加マスキング」を記録**する。③**構造的除外**（主）— 単価・エンド企業名（`BR-12`）は**そもそもプロンプトの組み立てに含めない**（除去するのではなく、入れない） |

#### 4.3.3 🔴 管理平面のバイパス方式（`CLAUDE.md` §10.5 / `docs/02` 章 7.4）

`CLAUDE.md` §10.5 は「**分離のバイパスは専用の DB ロール経由に限定し、主平面のアプリ経路と物理的に分離する。汎用のエスケープハッチを作らない**」と定める。

| 項目 | 内容 |
|---|---|
| **対応機能** | `F-055`〜`F-063`。`BR-36`〜`BR-44` |
| **採用** | 🔴 **専用 DB ロール `app_platform` + 専用の接続プール + 専用の Prisma Client インスタンス（`packages/db/platform` として別エクスポート）の 3 点セット** |
| **DB ロール** | `app_platform` に、**分離を越えて読む必要があるテーブル・列に対してのみ `SELECT` を付与する**。🔴 **`BYPASSRLS` は付与せず、代わりに管理平面用の RLS ポリシー（`current_setting('app.platform_user_id') IS NOT NULL` の条件で読み取りを許可）を別途定義する**。「全部見える」ロールを作らない |
| 🔴 **見せないものの担保** | `CLAUDE.md` §10.5 の「運営者にも見せないもの」（外部サービスのトークン平文 / **スキルシートの原本と本文** / エンジニアの氏名・生年月日・連絡先 / チャットの本文）は、**列レベルの `GRANT` で `app_platform` から外す**。アプリ層のマスキングだけに頼らない。**S3 に対しても `s3:GetObject` を管理平面のロールに付与しない**（§3.6） |
| **接続プールの分離** | 🔴 **管理平面は主平面と別の `DATABASE_URL`（`PLATFORM_DATABASE_URL`）を使う。** 同じプールを共有すると、`SET LOCAL` の設定ミスで主平面のリクエストが `app_platform` の権限で走りうる |
| **呼び出し経路の分離** | 🔴 **`packages/db` は `withTenant`（主平面）と `withPlatform`（管理平面）を別モジュールからエクスポートし、ESLint の `no-restricted-imports` で `apps/web/app/(main)/**` から `withPlatform` の import を禁止する**（`docs/02` 章 7.4「主平面のコードから分離を越える経路を呼び出せない」） |
| **監査の担保** | 🔴 **`withPlatform` は「操作者 `platform_user_id` / 理由 / 対象」を必須引数に取り、`AuditLog` への書き込みが成功してからでないとクエリを実行しない**（`docs/05` 申し送り 9「監査ログの記録失敗時に操作を成立させない」）。**引数を省略できないため、記録されない管理平面アクセスが型として作れない** |
| **代理閲覧（`F-060`）** | `withPlatform` の上に `withImpersonation` を重ね、**①理由 ②時間制限（`expires_at`）③read-only（書き込み系の Prisma 操作を拡張で拒否）④`ImpersonationSession` + `AuditLog` ⑤対象組織の管理者への通知**の 5 条件を**すべて引数と戻り値の型で強制する**（`docs/02` `F-060 AC-1`〜`AC-6`） |

### 4.4 トークン・秘匿情報の暗号化方式

| 項目 | 内容 |
|---|---|
| **対応機能** | `F-049`（電子署名の接続情報）/ `F-007`（招待トークン）/ `F-003`（2FA シークレット）/ Webhook のシークレット。`BR-25` / `docs/02` 章 7.3 |
| **採用** | **AES-256-GCM（Node.js 標準 `node:crypto`）による封筒暗号化。鍵は `TOKEN_ENCRYPTION_KEY`（32 バイトの base64）を `packages/config` で検証して読む** |
| **保存形式** | `v1:{key_id}:{iv_base64}:{ciphertext_base64}:{authTag_base64}` の 1 カラム文字列。🔴 **`key_id` を前置することでローテーションが可能になる**（新しい鍵で書き、古い鍵で読めるようにする） |
| **AAD（追加認証データ）** | 🔴 **`tenant_id` + カラム名を AAD に入れる。** これにより、**テナント A の暗号文をテナント B の行にコピーしても復号に失敗する**（DB を直接触られたときの横展開を防ぐ） |
| **鍵管理** | Phase 0〜2 は環境変数（`TOKEN_ENCRYPTION_KEY` / `TOKEN_ENCRYPTION_KEY_PREVIOUS`）。**Phase 3 で AWS KMS のデータキー方式へ移行する**（電子署名の資格情報を扱い始めるため）。判断: `pm` が Phase 3 の計画時 |
| **ローテーション** | ①新鍵を `TOKEN_ENCRYPTION_KEY` に、旧鍵を `TOKEN_ENCRYPTION_KEY_PREVIOUS` に設定 → ②新規書き込みは新鍵 → ③再暗号化ジョブが全件を新鍵に書き換え → ④旧鍵を外す。**②〜④の間、両方の鍵で復号できる** |
| **競合** | `pgcrypto`（DB 側で暗号化）→ **採らない。鍵が DB に近くなり、DB のバックアップ流出時に一緒に漏れうる**。Vault / KMS 直接 → Phase 3 で採用 |
| **リスク・回避策** | 🔴 **平文が `console.log` / Sentry / `AuditLog` / LLM プロンプトに出る事故**。**回避**: 暗号化フィールドを `EncryptedString` のブランド型にし、**`toJSON()` / `toString()` が `'[REDACTED]'` を返すクラスでラップする**。加えて §4.10 の Sentry `beforeSend` denylist とログのマスキングで二重に防ぐ |

|---|---|

| **性能は足りるか** | LLM 呼び出しは 1 回あたり 1〜10 秒かかる。**カウンタ更新の 1〜2 ms は無視できる。** メールも同様。**判定の頻度がボトルネックになる設計ではない** |
| **Redis の役割** | 画面表示用のキャッシュ（`F-027` の残量表示）と、**グローバルなトークンバケット**（正確性より平準化が目的なので揮発してよい） |
| **競合状態** | 🔴 **「判定 → 呼び出し → 記録」の間に別のジョブが呼び出すと上限を超えうる。** **回避**: 呼び出し**前**に見積りコストで加算（予約）し、呼び出し後に実コストで補正する。**予約に失敗（上限超過）したら呼び出さない** |

### 4.6 ジョブのスケジューリング

| 項目 | 内容 |
|---|---|
| **対応機能** | `F-043`（満了アラート）/ `F-026`（日次集計）/ `F-046`（保持期間削除）/ `F-054`（sandbox 期限）/ `F-064`（削除）|
| **採用** | **BullMQ の Repeatable Jobs（cron 式）。ワーカー基盤上で単一のスケジューラプロセスが起票する** |
| **時刻精度** | **分単位で足りる。** `docs/02` 章 7.1 は「満了アラートの日次照合は 1 時間以内に完了」であり、**起票時刻の精度は要件になっていない** |
| 🔴 **タイムゾーン** | **すべて `Asia/Tokyo` で判定し、DB には `timestamptz`（UTC）で保存する。** `docs/02` A-09 のとおり対象市場は日本国内のみ。**組織別のタイムゾーン設定を持たない**（持つと「満了 60 日前」の定義が組織ごとに揺れ、`BR-34` の「取りこぼし 0 件」の判定基準が曖昧になる） |
| **組織別か固定か** | 🔴 **固定（`Asia/Tokyo`、毎日 03:00 JST）。** 組織ごとの実行時刻を持たない。理由は上記に加え、**「テナントごとに違う時刻に走る」構造が `F-059` の未起票検知を複雑にする**ため |
| 🔴 **取りこぼしの防止** | **起票条件を「日付一致」ではなく「60 日前を過ぎ、かつ未起票」にする**（`docs/05` 申し送り 8 / `F-043 AC-4`）。**これによりジョブのスケジューリング精度が SLA に影響しなくなる** — ジョブが 1 日止まっても翌日に取り返す |
| **多重起動の防止** | Repeatable Job の `jobId` を `{jobName}:{yyyy-mm-dd}` にして、**同じ日に 2 回起票されても 1 回しか実行されない**ようにする |
| **リスク・回避策** | ⚠️ **スケジューラプロセスが死ぬと誰も起票しない。** **回避**: ①ワーカー基盤のヘルスチェックで再起動 ②**「最終実行時刻」を DB に記録し、24 時間以上更新が無ければ `F-059` にアラートを出す**（`docs/02` 章 7.9）。🔴 **`BR-34` は「取りこぼし 0 件（許容しない）」なので、ジョブの生存監視自体を運営平面の監視項目に入れる** |

### 4.7 冪等性キーの生成・保存方式

| 項目 | 内容 |
|---|---|
| **対応機能** | `F-022`（提案送信）/ `F-041`（面談調整）/ `F-047`・`F-049`（契約書送付・電子署名）。`BR-21` / `BR-22` / `docs/02` 章 7.8 |
| 🔴 **生成規約** | **`{entity}:{entity_id}:{attempt_seq}` の決定的な文字列。** 例: `proposal:018f...:1`。`attempt_seq` は**人間が明示的に再送したときにのみ増える**（`ProposalSendAttempt` の行数） |
| **なぜ乱数 UUID にしないか** | 🔴 **乱数だと「同じ送信の再実行」と「人間が意図した再送」を区別できない。** ジョブが 2 回起動したときに別のキーになり、**冪等性キーとして機能しない** |
| **保存** | `SendAttempt(entity_type, entity_id, attempt_seq, idempotency_key, external_id, status, created_at)`。🔴 **`UNIQUE(entity_type, entity_id, attempt_seq)` と `UNIQUE(idempotency_key)` の両方を張る** |
| **CAS との組み合わせ** | ①`Proposal` を `APPROVED` → `SUBMITTING` に CAS 更新（更新件数 1 が条件）→ ②`SendAttempt` を `INSERT`（一意制約違反なら既に送信済み → 終了）→ ③外部 API 呼び出し → ④結果を確定。🔴 **②で一意制約違反が起きたら、外部 API を呼ばずに終了する** |
| **外部 API がキーを受け取らない場合** | 🔴 **SES / クラウドサインとも冪等性キーの受け口が確認できていない**（§3.1.4 / §3.2）。**その場合、上記の①②が唯一の防御線である。したがって「①②を経ずに外部送信する経路」をコードとして作らせない** — `packages/connectors` の送信関数が `SendAttemptToken`（②の成功でのみ生成される値）を必須引数に取る |
| **リスク・回避策** | ⚠️ **③の後にプロセスが落ちると `SUBMITTING` のまま滞留する。** **回避**: `docs/02` 章 7.9 の「`SUBMITTING` 滞留」を `F-059` で検知し、**人間が到達を確認して確定させる**。🔴 **自動で `SUBMIT_FAILED` に落とさない**（落とすと自動再送の誘因になる） |

### 4.11 Webhook 受信の共通基盤

| 項目 | 内容 |
|---|---|
| **対応機能** | `F-011`（GuardDuty）/ `F-022`・`F-039`（SES のバウンス・苦情）/ `F-049`（電子署名）/ `F-062`（Stripe） |
| **採用** | 🔴 **「受信 → 検証 → `WebhookDelivery` に記録 → 即座に 200 を返す → 処理はジョブ」の共通パイプライン**を `apps/web/app/api/webhooks/[provider]` に 1 本置く |
| **理由** | ①**クラウドサインは 4xx を成功扱いにして再送しない**（§3.1.5）ため、受信時のバリデーション失敗で 4xx を返すと通知が永久に失われる ②SES(SNS) / GuardDuty / Stripe はいずれも **at-least-once** であり重複が来る ③検証方式がサービスごとに違う |
| **署名検証** | Stripe: `constructEvent`（必須）／SES(SNS): SNS のメッセージ署名（必須）／GuardDuty: EventBridge → 自前の受信であれば HMAC を自分で載せる／**クラウドサイン: 署名検証が無い（§3.1.5）→ URL パスの推測不能なシークレット + 受信後の API 再照会で代替する** |
| **冪等性** | `WebhookDelivery(provider, external_event_id)` に `UNIQUE`。**`external_event_id` が無いプロバイダ（クラウドサイン）は `(provider, document_id, status)` を代替キーにする** |
| **リスク・回避策** | ⚠️ **Webhook が届かないケース**（設定ミス・障害）。**回避**: **各連携に「最後に Webhook を受け取った時刻」を持ち、想定より長く途絶えたら `F-059` に出す**。加えて、**状態が中間状態のまま N 分滞留したエンティティを定期的にポーリングで照会する**（`Contract` の `UNDER_REVIEW`、ファイルの `SCANNING`） |

| 5 | **閲覧の記録** | ホストによる匿名候補一覧の閲覧を `AuditLog` に記録する（`BR-27` / `BR-28` の精神）。**「誰がいつどの案件で匿名候補を見たか」を後から説明できる** |

🔴 **未決の論点（人間の判断が必要）**: 上記 5 項目の粒度が「これで十分に粗いか」は、**取引先が実際に受け入れるかという業務判断でもある**。**誰が: 人間（`CLAUDE.md` §8.6）。いつ: Phase 1 の `F-016` / `F-017` の実装着手前。何をもって: 本節の粒度案に対する取引先候補 1〜2 社へのヒアリング、または事業側の判断。** 回答が来るまでは本節の値を既定として進める。

#### 4.18.1 環境ごとのデプロイ構成

| 環境 | Vercel | ワーカー | DB | AWS アカウント | 外部 API |
|---|---|---|---|---|---|
| `development` | ローカル（`next dev`） | ローカル（コンテナ） | ローカル PostgreSQL | **なし**（MinIO / MailHog / ClamAV で代替） | **すべてモック** |
| `demo` | Vercel Preview（固定ブランチ） | ECS（demo クラスタ） | RDS（demo インスタンス） | **非本番アカウント** | **すべてモック** |
| `sandbox` | Vercel Production（別プロジェクト） | ECS（sandbox クラスタ） | RDS（**sandbox 専用インスタンス**） | 🔴 **非本番アカウント。SES は「サンドボックス状態のまま」** | 送信系は宛先の分類で分岐（§3.2.8） |

#### 4.18.2 起動時 DI の実現方式（`docs/02` 申し送り 8 / NFR-ENV-2〜4）

```
packages/config/src/env.ts       … Zod スキーマ。APP_ENV と全環境変数を検証
packages/connectors/src/index.ts … createConnectors(env) が APP_ENV で実装を決める（唯一の分岐点）
```

| 要件 | 実現 |
|---|---|
| **NFR-ENV-2**（起動時 1 箇所の DI） | 🔴 **`createConnectors(env)` を `apps/web` / `apps/worker` の起動時に 1 回だけ呼び、結果を DI コンテナに入れる。** リクエストごとに呼ばない。**ESLint `no-restricted-imports` で、モック実装のモジュールを `packages/connectors/src/index.ts` 以外から import することを禁止する**（分岐の存在を静的に検出できる） |
| **NFR-ENV-3**（`production` でモックなら起動失敗） | 🔴 **`createConnectors` の内部で、`env.APP_ENV === 'production'` かつ選択された実装がモックなら `throw` する。** 「未設定ならモックにフォールバック」の分岐を**書けない構造**にする — Zod スキーマ側で、`APP_ENV === 'production'` のとき実装の必須環境変数を `required` にする（`z.discriminatedUnion('APP_ENV', [...])`） |
| **NFR-ENV-4**（非本番に本番キーがあれば起動失敗） | 🔴 **`packages/config` に「環境ごとに期待される固定値」を持たせて照合する。** 具体: `AWS_ACCOUNT_ID` / `SES_TENANT_PREFIX` / `STRIPE_SECRET_KEY` の接頭辞（`sk_live_` / `sk_test_`）/ `ANTHROPIC_API_KEY` のワークスペース。**`APP_ENV !== 'production'` で `sk_live_` を検出したら `throw`** |
| 🔴 **NFR-ENV-1**（`sandbox` の宛先分類） | **メール送信の単一経路 `sendEmail({ recipientClass, ... })` が `recipientClass` を必須引数に取る。** `recipientClass` は**列挙型であり省略できない**（TypeScript の必須プロパティ）。🔴 **さらに、呼び出し側に自己申告させず、`resolveRecipientClass(recipientUserId)` が `Membership` の `partner_company_id` の有無から機械的に導く**（`docs/05` 申し送り 10）。判定順は「`PlatformUser` → パートナー所属 → テナント所属 → それ以外」。**既定値を置く場合はモック側（分類 3）に倒す** |
| **二重防御** | §3.2.8 の第 2 層（SES サンドボックス）と第 3 層（環境変数の検証） |

#### 4.18.3 環境変数の管理

| 環境 | 管理場所 |
|---|---|
| `development` | `.env.local`（**コミットしない**）。`.env.example` をリポジトリに置く |
| `demo` / `sandbox` / `staging` / `production` | 🔴 **Vercel の Environment Variables（Web）と AWS Systems Manager Parameter Store / Secrets Manager（ワーカー）。** ワーカー側はコンテナに**平文の環境変数として渡さず、起動時に SDK で取得する** |

### 4.19 シードデータの生成方式

| 項目 | 内容 |
|---|---|
| **対応機能** | `F-053`（デモ環境の合成データ一式とリセット）。`CLAUDE.md` §5 Phase 0 の成功条件 |
| **採用** | 🔴 **TypeScript のシードスクリプト（`packages/db/seed/*.ts`）+ 固定シード値の疑似乱数（`seedrandom`）** |
| **なぜ fixture の JSON でなく スクリプトか** | ①**時系列データ**（進行中の提案、満了が近い稼働）は「実行日からの相対日数」で作る必要があり、静的な JSON では日付が古びる ②`docs/02` 章 7.6 のシード要件は「満了が近い稼働」「ゲートで止まる資料」を含み、**状態機械を正しく通した状態**でなければならない（DB に直接 INSERT すると不整合な状態が作れてしまう） |
| 🔴 **冪等な再生成** | **`reset()` → `seed()` の 2 段階。`reset()` は対象テナントのデータを削除し、`seed()` は固定シード値から同じデータを再生成する。** 同じ入力で同じ結果になる（`F-053 AC-2`） |
| 🔴 **時系列データの作り方** | **「実行日 = `T`」を基準に相対日で作る。** 例: 満了 55 日後の `Assignment`（`F-043` の 60 日前アラートが**次のジョブ実行で起票される**位置に置く）、7 日前に送信した `Proposal`（`INTERVIEW_SCHEDULED`）、3 日前にゲート FAIL した提案 |
| 🔴 **合成データの担保** | **実在の企業名・実在の個人名・実データ由来のスキルシートを含まない**（`F-053 AC-1`）。**企業名は「株式会社サンプルアルファ」等の明示的な架空名、氏名は架空名リストから生成、スキルシートはテンプレートから生成する。** 🔴 **`.gitignore` に実データ由来のファイルを入れる運用にしない — そもそもリポジトリに置かない** |
| 🔴 **実行できる環境の制限** | **`APP_ENV` が `demo` / `development` のときのみ実行でき、`production` / `sandbox` / `staging` では導線が存在せず API も拒否される**（`F-053 AC-6`）。**`packages/config` の Zod スキーマと API のミドルウェアの二重で拒否する** |
| **Phase 0 の分離テスト用** | **2 テナント × 2 パートナー**の最小シードを別スクリプト（`seed:isolation`）として持つ（`CLAUDE.md` §5 Phase 0） |

1. **損益分岐は 20 テナント規模で 1 テナント月額 ¥6,400（1 席 ¥215）である。** 国内 SaaS の一般的な席単価（¥3,000〜8,000）に対して**原価は十分に小さく、通常の利用では逆ざやにならない**。
2. 🔴 **逆ざやが起きるのは「AI 利用量が基準の 10 倍以上になったテナント」だけである。** 席単価 ¥3,000（テナント月額 $600）の場合、**AI 原価が $560 を超えると赤字**になる。基準の $12.82 に対して **44 倍**。§7.3 の感度分析で最悪ケース（8,000 回 × Sonnet 5）でも AI は $69 であり、**通常の使い方では到達しない**。

4. 🔴 **`Q-15`（プラン別 AI クォータの初期値）の候補**（**人間の判断事項**。`CLAUDE.md` §8.6）:

## 9. 将来の置き換え可能性

### 9.1 差し替えが想定される依存と、抽象の妥当性

| 依存 | 差し替えの可能性 | 抽象の場所 | 抽象は妥当か |
|---|---|---|---|
| **電子署名（クラウドサイン）** | 🔴 **高い。** BYO 接続方式のため、**テナントが GMO サインを使っていれば GMO サインに接続する必要がある**（§3.1.2）。Phase 3 の時点で 2 実装が並存しうる | `packages/connectors` の `EsignProvider`（`createAndSend` / `fetchStatus` / `withdraw` / `downloadExecuted`） | 🔴 **妥当。ただしテナント単位でプロバイダが変わる**ため、**`ESIGN_PROVIDER` の環境変数だけでなく、`TenantEsignConnection.provider` で実装を選ぶ経路が要る**。§4.18.2 の「起動時 1 箇所の DI」の例外になるため、**DI コンテナには「全プロバイダの実装のマップ」を入れ、テナント設定でキーを引く**構造にする（リクエストごとの `if` にしない） |
| **メール（Amazon SES）** | 低い。§3.2.1 の 3 要件（宛先 allowlist / テナント分離 / 独自ドメイン）を同時に満たす代替が見当たらない | `packages/connectors` の `EmailSender`（`send({ recipientClass, ... })`） | 🔴 **妥当。ただし `recipientClass` を必須にする設計は SES 固有ではなく本プロダクト固有の統制**であり、**インタフェース側に残す**（プロバイダを替えても統制が消えない） |
| **ウイルススキャン（GuardDuty）** | 中。`development` では ClamAV を使うため**最初から 2 実装ある** | `packages/connectors` の `MalwareScanner`（`enqueue` / `getResult`） | 妥当。**結果のステータスを内部型（`CLEAN` / `INFECTED` / `UNSCANNABLE` / `FAILED`）に正規化し、`UNSUPPORTED` を `CLEAN` に寄せない**（§3.4.3-3） |
| **オブジェクトストレージ（S3）** | 低い。GuardDuty が S3 に依存する（§3.6） | `packages/connectors` の `ObjectStore` | 妥当。ただし 🔴 **「S3 互換に留める」という規律を破ると差し替え不能になる**。**S3 固有機能（Object Lambda / Intelligent-Tiering 等）を業務ロジックから使わない** |
| **AI（Anthropic）** | 🔴 **`CLAUDE.md` §6 で明示的に対象外。抽象化しない** | `packages/ai`（プロバイダ抽象ではなく**ロール抽象**） | 🔴 **妥当かつ意図的。** `packages/ai` はロール（`sheet-parser` 等）でインタフェースを切る。**プロバイダで切ると「切替可能性のために統制を緩める」ことになり `CLAUDE.md` §3.2 に反する**。プロバイダ障害のリスクは事業として引き受ける（`docs/02` 章 9） |
| **課金（Stripe）** | 低い。日本の適格請求書対応（§3.8.4）が乗り換えの障壁 | `packages/connectors` の `BillingProvider` | 🔴 **薄い抽象で十分。** メータリングの「正は自社カウンタ」（§3.8.3）が守られていれば、課金基盤を替えても業務データは影響を受けない |
| **ホスティング（Vercel）** | 中。§8.2 のとおり **SSE の分離**でワーカー側の比重が増える | Next.js の標準機能に留める | 🔴 **Vercel 固有機能（Edge Config / KV / Blob）を使わない**という規律で担保する。**使うと移行不能になる** |
| **DB（PostgreSQL）** | 🔴 **極めて低い。RLS への依存が構造的**（`CLAUDE.md` §3.1） | — | 🔴 **抽象化しない。** RLS は本プロダクトの安全性の土台であり、**「他の DB にも移せるように」RLS を使わない設計にすることは本末転倒**である |
| **検索（PostgreSQL 全文検索）** | 中。§3.7.3 の段階 4 で OpenSearch を入れる可能性 | `packages/db` の `searchEngineers` / `searchProjects` | 🔴 **クエリを 1 箇所に閉じておく。** ただし **RLS を経由しない検索エンジンに移すと、テナント分離の担保がアプリ層だけになる**。**移行時は「検索は ID のリストだけを返し、本体は必ず RLS 越しに取り直す」構造にする**（`docs/05` へ） |

### 9.2 抽象を作らないと決めたもの（意図的な判断）

### `program-design`（`docs/05`）へ

1. 🔴 **`withTenant` は必ず `$transaction` を開き、その先頭で `SET LOCAL app.tenant_id` / `app.partner_company_id` を発行する**（§4.3.1）。**トランザクション外の `SET` を書かない。** アプリ用 DB ロールは `BYPASSRLS` を持たず、マイグレーション用ロールと分ける。
2. 🔴 **管理平面のバイパスは「専用 DB ロール `app_platform` + 専用接続プール（`PLATFORM_DATABASE_URL`）+ 専用 Prisma インスタンス」の 3 点セット**（§4.3.3）。**`withPlatform` は操作者・理由・対象を必須引数に取り、`AuditLog` の書き込み成功後でないとクエリを実行しない。** 主平面のコードから `withPlatform` を import できないことを ESLint で担保する。**`CLAUDE.md` §10.5 の「運営者にも見せないもの」は列レベルの `GRANT` で外し、S3 も `s3:GetObject` を付与しない。**
3. 🔴 **冪等性キーは `{entity}:{entity_id}:{attempt_seq}` の決定的な文字列**（§4.7）。**乱数 UUID にしない**（「同じ送信の再実行」と「人間が意図した再送」が区別できなくなる）。`SendAttempt` に `UNIQUE(entity_type, entity_id, attempt_seq)` と `UNIQUE(idempotency_key)` を張り、**`packages/connectors` の送信関数が `SendAttemptToken` を必須引数に取る**（CAS と INSERT を経ずに外部送信できない構造にする）。
4. 🔴 **クラウドサインには冪等性キーが確認できない（U-1）。Webhook にも署名検証が無い**（§3.1.5）。したがって ①**Webhook の受信 URL にテナントごとの推測不能なシークレットをパスに含める** ②🔴 **Webhook のペイロードで状態を確定させず、必ず API で再照会してから遷移させる** ③**受信を冪等にする**（`UNIQUE(provider, external_document_id, status)`）④🔴 **受信エンドポイントは即座に 200 を返し、処理はジョブに積む**（400 番台は再送されないため、バリデーション失敗で 4xx を返すと通知が永久に失われる）。
5. 🔴 **メール送信の単一経路は `recipientClass` を必須引数に取り、`resolveRecipientClass(recipientUserId)` が `Membership` から機械的に導く**（§4.18.2 / `docs/02` 申し送り 10）。**呼び出し側に自己申告させない。既定値を置く場合はモック側（分類 3）に倒す。** 判定順は「`PlatformUser` → パートナー所属 → テナント所属 → それ以外」。
6. 🔴 **`sandbox` は「アプリ層の分類 + SES サンドボックス + 環境変数検証」の三重防御にする**（§3.2.8）。`sandbox` は本番と別の AWS アカウントを使い、**SES をサンドボックス状態のままにする**（検証済み宛先にしか送れない）。**identity の追加は運営者の手動操作に限定する。**
7. 🔴 **BullMQ の送信系キューは `attempts: 1` 固定**（§2.1 / §4.7）。**キュー生成を `packages/connectors` の 1 箇所に閉じ、`attempts > 1` を送信系キューに設定できない型にする。** キューの抽象化レイヤを作らない（§9.2。抽象化すると「自動リトライを禁止できていること」がコードから見えなくなる）。
8. 🔴 **利用量カウンタは DB を正とし、Redis は表示用キャッシュとトークンバケットに限る**（§4.5）。`INSERT ... ON CONFLICT DO UPDATE ... RETURNING` で原子的に加算する。**呼び出し前に見積りコストで予約し、呼び出し後に実コストで補正する**（予約に失敗したら呼び出さない）。
9. 🔴 **`match-explainer` は複数候補（既定 10）を 1 リクエストにまとめる**（§7.3-2 / §8.1-7）。**候補ごとに 1 リクエストにすると、Anthropic の RPM が最初の律速になる。**
10. 🔴 **LLM の構造化出力は `output_config.format` + `zodOutputFormat` を使い、受信後に必ず Zod で `safeParse` する**（§3.3.3 / §4.1）。**JSON Schema 側は `minimum` / `maxLength` 等の制約を無視するため、受信後の再検証が唯一の担保である。**
11. 🔴 **`packages/ai` の LLM 呼び出し関数は `image` / `document` コンテンツブロックを型として受け取れないようにする**（§4.2）。**画像を送れない構造にすることで、`CLAUDE.md` §7 の「PII 未マスキング送信 0 件」を型で担保する。** マスキング済みのテキストは `MaskedText` のブランド型にする。
12. 🔴 **暗号化は AES-256-GCM。`v1:{key_id}:{iv}:{ct}:{tag}` の形式で保存し、AAD に `tenant_id` + カラム名を入れる**（§4.4）。**暗号化フィールドは `toJSON()` / `toString()` が `'[REDACTED]'` を返すクラスでラップする**（キー名の denylist に頼らない防御）。
