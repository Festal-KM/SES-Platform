## 1. 連絡経路とエスカレーション

### 1.1 🔴 順序 —— まず止める、次に記録する、その後に連絡する

**事故（誤送信・情報漏洩の疑い・長時間の停止）を検知したら、この順序を守る。** 連絡を先にすると、連絡している間に被害が増える。記録を後回しにすると、何が起きたかを後から説明できなくなる（SES では「誰の経歴を、誰が、いつ見たか」が説明責任の対象である。`CLAUDE.md` §3.5）。

#### ① まず止める

🔴 **運営者は業務データを書き換えられない**（`CLAUDE.md` §10.5 の既定 read-only。`app_platform` は業務テーブルに `SELECT` のみ、`app_platform_write` は業務テーブルへの書き込み権限を一切持たない）。したがって「止める」の実体は次の 3 つしかない。

| 手段 | 何が止まるか | 誰が | 入口 |
|---|---|---|---|
| **テナントの停止**（`ACTIVE` → `SUSPENDED`） | 🔴 **実行系（提案の承認・送信、契約書の送付・電子署名依頼、面談調整の連絡、提案依頼の発行）が一切できなくなる。ログインと閲覧はできる。データは削除されない** | 🔴 **`PLATFORM_OWNER` のみ**（`PLATFORM_SUPPORT` には導線が存在しない） | `A-010` = `/admin/tenants/{id}/contract`。**確認ステップ**（理由の必須入力 + テナント名の入力）は省略できない |
| **ワーカーの停止** | 送信ジョブ・ゲート・スケジュール実行がすべて止まる。🔴 **副作用が大きい**（`SUBMITTING` の確定〔`send.settle-unknown`〕・保留の自動復帰〔`send.hold-release` / `gate.hold-release`〕・削除予告・計測もすべて止まる。§2.2 のスケジューラ行） | 技術エスカレーション先（**未定**） | コンテナ基盤（**手順は未定。§9**） |
| **テナント利用者への操作停止の依頼** | 人の判断に依存する | 一次受け（**未定**） | 当該テナントの `OWNER` / `ADMIN` |

🔴 **DB に直接 `UPDATE` して状態を戻すことで「止め」ない**（§8-5）。

#### ② 次に記録する

- **運営者の全操作（閲覧を含む）は `AuditLog` に自動で残る**（`withPlatformRead` / `withPlatformWrite` が `fn` の前に書く。`CLAUDE.md` §10.5 / `docs/05` §5.3）。**記録されない管理平面アクセスは型として作れない。**
- 🔴 **自動で残らないのは「見て、こう判断した」である。** 時刻・見た画面・読み取った件数・打った手を人が書き残す。`A-005` は**最終更新時刻を秒単位で表示する**ので、その値を控える。
- 🔴 **`AuditLog` の内容を書き換えない・消さない**（編集・削除は DB 権限で禁止されている。`docs/05` §16.1）。

#### ③ その後に連絡する

§1.3 の類型に当たるなら、§1.2 の経路で上げる。

### 2.2 毎日見る項目（`docs/05` §16.5 / `docs/04` §A-005 の項目表。**項目番号と名称はそのまま**）

🔴 **項目 8 / 9 / 10 は Phase 2・Phase 3 であり、第 1 回リリース時点の画面には存在しない**（8 = 満了 60 日前の未起票 / 9 = 匿名候補の一意率 / 10 = `SENDING` の滞留・未対応 `SEND_FAILED`・電子署名の未着）。

| 項目 | 何が起きているか | 誰が見るか | 最初にやること |
|---|---|---|---|
| **1. 未対応の送信失敗（`SUBMIT_FAILED`）** | 外部への送信が失敗（または応答不明で確定）し、**まだ誰も再送していない提案**。🔴 閾値を掛けず**全件が未対応**（この状態からの復帰は人間の再送だけであるため） | 一次受け（`PP` 可）。**対処はテナント利用者** | 行から `A-003`（`/admin/tenants/{id}`）でテナントを特定 → テナント利用者に **§4 の手順**を案内する。🔴 **運営者は再送できない**（管理平面に再送 API は無い）。🔴 `LOST` / `GATE_FAILED` / `DECLINED` は含まれない |
| **2. 送信中（`SUBMITTING`）の滞留** | 片道の状態に入ったまま、閾値（`SUBMITTING_STALL_ALERT_MINUTES`。既定 30 分）を超えて確定していない | 一次受け | 🔴 **何もしない。状態を書き換えない**（管理平面に確定 API は無い）。閾値 + 最大 10 分で `send.settle-unknown` が `SUBMIT_FAILED` に確定させる。**それを超えて残るならジョブが動いていない** → 項目 3 と「スケジューラの生存」を見る。確定後は項目 1 で追う |
| **3. 失敗ジョブ** | ジョブキューの failed。ジョブ種別 / 件数 / 最終失敗日時 | 一次受け → 技術エスカレーション | キュー名を見る。**`send.*`**（`attempts: 1`）→ §4 / **`gate.run`**（`attempts: 1`）→ §5 / **それ以外**（`attempts` 2〜3）は自動再試行を使い切った失敗 → Sentry の同時刻の例外と突き合わせる。🔴 **運営者の再実行操作は存在しない**。🔴 AI の上限による保留はここに含まれない |
| **4. ウイルススキャン失敗** | `INFECTED`（感染を検出）/ `UNSCANNABLE`（検査不能）/ `FAILED`（検査失敗）/ `SCANNING` のまま閾値超過（`SCAN_STALL_ALERT_MINUTES`） | 一次受け | 🔴 **`CLEAN` になるまで共有 URL は発行されないため、外部流出は起きていない**（`CLAUDE.md` §3.4）。テナントに再アップロードを案内する。`SCANNING` 滞留が広範ならスキャナ側（GuardDuty）の障害を疑う |
| **5. ゲート FAIL 率** | 確定した実行（`DONE`）のうち、いずれかの層が FAIL だった割合と、その急変 | 一次受け | 🔴 **FAIL 率が高いこと自体は障害ではない**（ゲートが仕事をしている）。**急変のときだけ**、直前のプロンプト版 / モデル設定の変更を疑う。🔴 **AI の日次コスト上限による保留は分母にも分子にも含まれない**。🔴 **FAIL を迂回して送る導線は無い**（§8-3） |
| **6. 計測欠測・ストレージの乖離** | `欠測` / `不一致` / `ストレージの乖離`。🔴 **後から遡って計測できない** | 一次受け（**最優先**） | 欠測日を控え、**ワーカーの停止時間と突き合わせる**。🔴 **ワーカー停止中の日の不一致は自動では直らない**。`demo` のストレージ乖離は検算対象外（web と worker が別のモックを持つため常に乖離する） |

## 4. 送信失敗（`SUBMIT_FAILED`）からの復帰

### 4.1 🔴 原則 —— 復帰は人間の明示操作のみ

> **`SUBMITTING` は片道である。** 入ったら必ず `SUBMITTED` か `SUBMIT_FAILED` に確定させる。**自動リトライしてはならない**（二重送信事故になるため）。再送は人間の明示操作のみ。
> **`SUBMIT_FAILED` からの復帰は人間の操作に限る。**
> —— `CLAUDE.md` §4.2

**なぜ自動リトライしないか**: 🔴 **取引先への二重送信・誤送信が本プロダクト最大の事故である**（`CLAUDE.md` §3.4 / §7 の「0 件（許容しない）」）。**外部 API 呼び出しの結果が確定した後にリトライしてはならない。**

**実装上の担保**（知っておくこと。運用で気をつける話ではない）:

| 手段 | 実装 |
|---|---|
| キュー設定 | `send.proposal` / `send.interview-invite` / `send.contract` は **`attempts: 1` を型で固定**（`attempts: 2` はコンパイルエラー） |
| `attempt_seq` の採番 | 🔴 **人間の明示操作（`POST /api/proposals/{id}/resend`）でのみ増える。** ジョブ側で採番しない |
| API の要件 | `POST /resend` は **`{ acknowledged: true }` を必須**にする（無ければ **400 `RESEND_NOT_ACKNOWLEDGED`**。行を読む前に落ちる） |
| 状態遷移の制約 | `SUBMIT_FAILED → APPROVED` を起こすコードは **`apps/web/lib/proposals/resend.ts` の 1 箇所だけ**。`tests/static/proposal-resend-human-only.test.ts` が、この遷移が `apps/worker/**` に無いことを AST で固定する |
| 管理平面 | 🔴 **運営者は再送できない**（`app_platform*` に `proposals` への書き込み権限が無い） |

### 4.2 手順（実在の導線）

| # | 手順 | 画面 / API |
|---|---|---|
| 1 | 運営者が `A-005` **項目 1** で対象テナントを特定する → `A-003`。🔴 **運営者はここまで**（提案の内容・宛先には到達しない） | `/admin/monitoring` → `/admin/tenants/{id}` |
| 2 | テナント利用者（`OWNER` / `ADMIN` / `SALES`）が **`S-022` 送信失敗の一覧**を開く。`VIEWER` には再送の導線が無い。**取引先はこの画面に到達しない**（送信はホストが行う） | **`/proposals/send-failures`**（`S-003` の要対応キューの「送信失敗」行 / `S-019` の一覧 / `S-021` からも到達する） |
| 3 | 行を選び、**失敗理由**を確認する。🔴 **`応答不明（到達したか確認できない）` と `送信に失敗した` は別の語**であり、再送の判断が変わる。他の理由: `送信元ドメインが未検証` / `認証エラー` / `宛先アドレスが無効` / `送信上限に達した` / `外部サービスの障害` | `S-022` セクション 3 |
| 4 | 先方に未着かどうかを確認する。🔴 **外部への照合は「実行されていた」は断定できるが「されていなかった」は断定できない**（反映遅延・相手側での削除・取得失敗が同じ結果に見える）。**照合は人間確認の補助であって、確認の省略の根拠にしない** | — |
| 5 | **確認ステップ**: 「**この提案は先方に届いている可能性があります。届いていないことを確認してから再送してください**」+ 提案先・エンジニア・単価の再掲 + 最終試行日時。🔴 **「届いていないことを確認した」のチェックと理由の入力の両方**を満たさないと押せない | `S-022` の確認ダイアログ → `POST /api/proposals/{id}/resend`（`{ acknowledged: true, reason }`） |
| 6 | `SUBMIT_FAILED → APPROVED` の CAS → **新しい `attempt_seq` と新しい `idempotency_key`** で送信ジョブ。状態バッジが `送信中` へ。**確定するまで再度の再送操作は選択できない** | — |

- **理由が「送信元ドメインが未検証」の場合**: 🔴 **再送ではなく検証が先**。`S-036`（**`/settings/sending-domains`**）で検証する。検証が通れば `send.hold-release` が保留を自動復帰させる。
- **再送も失敗した場合**: 再度この一覧に戻り、再送回数が増える。**回数が 3 回を超えた行には「繰り返し失敗しています。運営に問い合わせてください」が出る** → §1.2 の一次受けへ。
- **記録**: 再送の指示者・日時・理由は `ProposalEvent.note`（全文）と `AuditLog`（`proposal.resend`。`summary` には理由の**文字数**だけ）に残る。

### 4.3 🔴 「まとめて再送」は存在しない

- **一括再送の導線は実装されていない。** 行ごとの 1 操作だけであり、**モバイルでも同じ**（1 件ずつの再送は可能だが、確認ステップは省略されない）。
- `docs/04` §S-022 はデスクトップの一括再送を将来の選択肢として書くが、**一括でも確認ステップは 1 件ずつの内容を列挙する必要がある**ため Phase 1 では置いていない（`apps/web/app/(main)/proposals/send-failures/send-failure-screen.tsx` 冒頭注記 ③）。

### 4.4 `SUBMITTING` の滞留が出たとき（`A-005` 項目 2）

## 5. `gate.run` の失敗ジョブの再実行

### 5.1 🔴 入口は API #39 だけ。キューに直接積む経路は無い

`gate.run` は `attempts: 1`（再試行は `runRole` 内部で完結し、ジョブ再実行は `AiUsage` を二重に積むため）。失敗すると提案は **`GATE_RUNNING` のまま滞留**し、承認にも送信にも進めない（`A-005` 項目 12 の `ジョブ失敗`、および項目 3）。

🔴 **再実行の入口は、テナント利用者の API #39 `POST /api/proposals/{id}/gate`（画面では「レビュー依頼」）だけである。**

- 🔴 **運営者向けの retry 操作は作らない**（[Issue #16](https://github.com/Festal-KM/SES-Platform/issues/16) で 2026-09-01 に決定）。運営者は `A-005` 項目 12 で滞留を検知し、**テナント利用者に再依頼を促すだけ**である。
- 🔴 **作ろうとしても権限で弾かれる**: `app_platform*` に `proposals` / `review_gates` の書き込みが無い（`CLAUDE.md` §10.5 の既定 read-only）。静的テスト `tests/static/admin-no-gate-retry.test.ts` が、管理平面に `bullmq` / キュー生成器 / `Job.retry()` / `removeFailedJob()` / `proposals`・`review_gates` への書き込み / 生 SQL が無いことを固定する。
- 🔴 **BullMQ の管理 UI やスクリプトからジョブを積み直さない**（§8-2）。

### 5.2 5 手順（`docs/05` §9.10 のまま）

| # | 手順 |
|---|---|
| ① | **入口はテナント利用者の #39 だけ**（作成者 / `SALES` / `ADMIN` の「レビュー依頼」を、`GATE_RUNNING` かつ HELD 行が無い対象 = `docs/05` §16.5 の `JOB_FAILED` に対しても受け付ける） |
| ② | DB トランザクションの**外**で `Queue.getJob(gateRunJobId(...))`（⚠️ 区切りは `.`）を取得し、**状態が `failed` のときだけ `Job.remove()`** で削除する。`waiting` / `active` なら削除しない（走っているものを止めない。この場合の再 enqueue は BullMQ の重複排除で no-op） |
| ③ | `withTenant(ctx)` で `review_gates(targetType, targetId, contentHash, execution='DONE')` が**無い**ことを確認し、あれば enqueue せず **422**（ワーカー開始時と同じ判定を API で先に行う） |
| ④ | **同じ payload・同じ `jobId`** で `gate.run` を enqueue |
| ⑤ | `Proposal` は 🔴 **`GATE_RUNNING` のまま**（状態を足さず、この時点では遷移も起こさない）。再実行の結果で `APPROVAL_PENDING` か `GATE_FAILED` に確定する |

**多重化防止**: HELD 行が無いので、`jobId` の重複排除（待機・実行中）と `DONE` 行チェック（確定後）の **2 段**で成立する。`gate.hold-release`（AI 上限からの自動復帰）は HELD 行だけを走査するため、失敗経路とは交差しない。

### 5.3 運用上の見え方

- 🔴 **手順 ② の削除で `A-005` 項目 3「失敗ジョブ数」が減るのは意図どおり**である（再依頼された failed は未対応ではない）。**「勝手に件数が減った」と読まない。**
- 画面の導線は **提案の編集（`S-020` = `/proposals/{id}/edit`）の「レビュー依頼」**。
- ⚠️ **内容を変えずに再依頼すると 422 `GATE_ALREADY_COMPLETED` になることがある**（同じ `contentHash` の確定行が既にある場合）。その場合は元データを直してから依頼し直す（🔴 **直せるのは元データだけである**。§8-3）。
- 🔴 **`保留`（`AI の日次コスト上限による停止`）に #39 は要らない。** `gate.hold-release` が上限解除後に自動で積み直す。**保留と失敗を混同して #39 を叩かせない**（§2.4）。

### 6.4 🔴 個人情報の保持期間との関係 —— **古いバックアップから復元すると、削除済みの個人情報が戻る**

> 🔴 **復元は「消したはずのものを戻す」操作である。** 削除の実行より前に取得したバックアップから復元すると、`F-064`（`tenant.purge`）/ `F-046`（`retention.delete`）が消した**エンジニアの連絡先・スキルシート原本・経験内容の行・チャット本文**が DB に戻る。

**知っておくこと**:

| 事実 | 出典 |
|---|---|
| `tenant.purge` は `CLOSING` → 30 日 → `PURGED` で、エンジニアの連絡先 / スキルシート原本 / チャット本文 / 経験内容の行を削除し、`lifecycle_state='PURGED'` にする。**`PURGED` は終端で、復帰遷移は `canTransition` の型に存在しない** | `CLAUDE.md` §4.2 / `docs/05` §9.7 / §10.7 |
| `retention.delete` は 🔴 **①S3 の `DeleteObject` → ②DB の列を NULL 化し `piiPurgedAt` を立てる の順**。①が失敗したら②に進まない | `docs/05` §9.7 / `docs/03` §4.12 |
| 起票条件はどちらも「**期限を過ぎ、かつ未処理**」である（日付一致ではない） | `docs/05` §9.7 |

**したがって復元後に起きること**:

1. **`piiPurgedAt` / `lifecycle_state` が巻き戻るため、削除は「未処理」に戻る。** `retention.scan` / `tenant.purge-scan` の次回実行で再び対象になりうる。ただし `tenant.purge-scan` は 🔴 **削除予告が配送済み**であることを要求するため、予告の `EmailDispatch` も巻き戻っていると **予告からやり直しになる**（`A-005` 項目 15 に出る）。
2. 🔴 **S3 のオブジェクトは DB の復元では戻らない。** DB は「原本あり」と言うが実体が無い行が生じうる。
3. 🔴 **どちらも自動で正しく収束するとは限らない。**

**やること（順序）**:

| # | やること |
|---|---|

| **1** | 🔴 **`production` でモック実装を選ぶ**（「未設定ならモックにフォールバック」を含む） | **成功したように見えて実際には送信されていない**という最悪の壊れ方を生む（`CLAUDE.md` §11.1） | **型と起動時検証で止まる**: `packages/config` の Zod スキーマの `production` の枝に `mock` が無い（`z.literal('mock')` が存在しない）。`production` でモックが選択されたら**起動を失敗させる**（`docs/05` §13.4 規則 1 / §13.1）。🔴 **止まったことを「回避」しない** |
| **2** | 🔴 **送信ジョブを手でリトライする**（BullMQ の retry、ジョブの再投入、キューへの直接 enqueue） | **取引先への二重送信 = 本プロダクト最大の事故**（`CLAUDE.md` §3.4 / §7 の「0 件」）。**外部 API 呼び出しの結果が確定した後にリトライしてはならない** | `send.*` は **`attempts: 1` を型で固定**。`attempt_seq` は人間の `POST /resend` でのみ増える。運営者の retry 操作は存在せず、`app_platform*` に `proposals` への書き込みが無い。`tests/static/admin-no-gate-retry.test.ts` / `proposal-resend-human-only.test.ts` が固定する。**復帰は §4 の手順だけ**（`CLAUDE.md` §4.2 / `docs/05` §9.10 / §10.6） |
| **3** | 🔴 **ゲート FAIL を回避して送る**（DB を直す / ゲートを飛ばす / 指摘を無視する運用にする） | **`CLAUDE.md` §3.3「ゲートの FAIL を『無視して送信』できる導線を作らない。直せるのは元データだけである」** | **`Proposal` は `APPROVED` を経ずに `SUBMITTED` に遷移できない**。**承認後に内容を変えると `contentHash` が変わり承認が無効になる**（`docs/05` §11.5。再検証と同一トランザクションで確定する）。🔴 **`gate-inspector`（AI）の指摘だけで FAIL にしない**代わりに、**機械的照合の FAIL は迂回できない** |
| **4** | 🔴 **本番データを他環境へコピーする**（`demo` / `development` / 検証用インスタンスを含む。**匿名化しての持ち出しも不可**） | エンジニアの氏名・スキルシートを含む（`CLAUDE.md` §11.1 / `BR-47`）。🔴 **`demo` に見込み客の実データを入れない** —— `demo` は営業が客先で見せる画面であり、**実演中に実在の取引先名が画面に出る事故**につながる（`CLAUDE.md` §11.1「`demo` と `sandbox` を兼ねない」/ `T-12-11` ⑧b / `docs/dev-plan.md` §2.2 RL-11） | 非本番は**合成データのみ**（`pnpm seed --preset=demo`。`APP_ENV ∈ {demo, development}` でのみ実行でき、`packages/config` の検証と API-A16 のミドルウェアの二重で拒否される）。静的テスト `tests/static/demo-seed-no-real-names.test.ts` がソースに実在名が無いことを固定する。**`SEED_DATABASE_URL` は `development` / `demo` の実行時環境にだけ置ける**（`docs/05` §13.4 規則 7） |
| **5** | 🔴 **DB に直接 `UPDATE` して状態機械を飛ばす**（`proposals.state` / `tenants.lifecycle_state` / `review_gates` などを SQL で書き換える） | **不正な遷移は `InvalidStateTransitionError`（422）で拒否される設計であり、サイレントに無視しない**（`CLAUDE.md` §4.2）。直接 `UPDATE` すると `ProposalEvent` / `AuditLog` / `SendAttempt` / `contentHash` の整合が崩れ、🔴 **二重送信の防御（`UNIQUE` + CAS）が効かなくなる** | 状態は `packages/domain` の `transition()` + `WHERE state = <from>` の CAS でしか進めない。**seed でさえ生 INSERT で状態を書かない**（`docs/05` §13.6）。🔴 **`MIGRATION_DATABASE_URL` をアプリの実行時環境に置かない**（全環境で起動が失敗する。`docs/05` §13.4 規則 3） |
| **6** | 🔴 **運営者が業務データを書き換える**（エンジニア・案件・提案・チャット・契約） | `CLAUDE.md` §10.5 の**既定 read-only**。書き込みが許されるのは**契約・クォータ・機能フラグ・お知らせ**と、**テナントの開設・初期 `OWNER` の招待・送信ドメインの登録（いずれも INSERT のみ）**だけ。🔴 **この列挙に無いものを「契約の一部だから」という解釈で足してはならない**（[Issue #21](https://github.com/Festal-KM/SES-Platform/issues/21)） | `app_platform` は業務テーブルに `SELECT` のみ、`app_platform_write` は 7 ドメインのみ。**書き込みメソッドを持つ管理平面 API は固定の 6 本**で、静的テストが固定する |
| **7** | 🔴 **保留（`HELD_*`）を失敗として数える / 保留に再送ボタンを付ける** | `CLAUDE.md` §4.2「失敗と保留を混同しない」。保留は**外部への送信を 1 回も試みていない**。人が押す再送と自動配送が多重化すると二重送信になる | `A-005` の項目が分かれている（項目 13 / 14 / 15 / 項目 12 の保留区分）。**再送の操作導線を置かない**（`docs/04` §A-005） |
| **8** | 🔴 **分離テストの判定を緩める・除外リストを広げて通す** | **このテストが防ごうとしている壊し方そのものである**（`docs/dev-plan.md` §6.4 R-05）。RLS が無効化されてもアプリは正常に動くため、**機能テストでは気づけない** | `tests/isolation/**` を CI で毎回走らせる。🔴 **`tests/isolation/**` は `dist` 越しに走るため、`pnpm -r build` を挟まないと防御を壊しても緑のままになる**（`docs/05` §11.13 ④）。**「緑だから守られている」と読むときは、ビルドを挟んだ実行であることまで確認する** |
