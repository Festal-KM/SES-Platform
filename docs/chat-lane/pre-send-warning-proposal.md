# 設計案: チャット本文の「送信前の注意」（#89 の中間案）

> **状態: 案（暫定）。** [#89](https://github.com/Festal-KM/SES-Platform/issues/89) で宮田・紺野の合意を取るまで実装しない。
> 合意後、`docs/02`（F-038）→ `docs/04`（§S-031）→ `docs/05`（§6.5 #51）の順に上流から反映する（`CLAUDE.md` §8.7）。
> 作成: 2026-10-14、チャットレーン（担当: 紺野）。

## 1. 結論

本文だけの投稿は **品質ゲートで止めない**。代わりに、**ホストの営業が書いた本文に、自社が登録したエンド企業名・単価らしき文字列が含まれていたら、送信の直前に注意を出す**。注意は「止める」ものではなく「気づかせる」ものであり、本人が確認すれば送れる。

| 項目 | 決め方 |
|---|---|
| ゲートの対象 | `CLAUDE.md` §3.3 の列挙どおり **チャット添付のみ**。本文は対象外（docs/02・docs/04 の側を CLAUDE.md に合わせて直す） |
| 本文の守り | 送信前の注意（本書）+ 既にある「このスレッドの参加会社にだけ表示されます」の常時表示 |
| 判定の手段 | **機械的な照合のみ**。AI（LLM）は使わない |
| 注意を出す相手 | **ホスト所属の利用者だけ**。取引先の利用者には出さない（§3） |

## 2. なぜ止めないのか

- `CLAUDE.md` §3.3 の「テナント外へ共有されるもの」の列挙は **チャット添付**であり本文ではない。列挙を広げるのは人間の承認事項（§8.6）
- 1 投稿ごとに `gate-inspector` を呼ぶと、会話の往復の速さで AI のクォータを消費する（`docs/04` §S-031 改訂 27 の理由②）
- チャットは「移動中のスマートフォンで返信する」Tier 1 の画面であり（§13）、送信のたびに止めると返信が遅れる

## 3. 情報境界（最重要）

🔴 **取引先の利用者に、ホストのエンド企業名と一致したことを知らせない。**
取引先の利用者が書いた本文に「この語はエンド企業名です」と出すと、それ自体がホストの商流情報（エンド企業名）を教えることになる（`CLAUDE.md` §3.1 経路 5 の「ホストの上流・エンド企業名は出さない」）。総当たりで語を試せば、エンド企業名を割り出せてしまう。

したがって:

- 照合は **ホスト所属の利用者（`OWNER` / `ADMIN` / `SALES`）が投稿するとき**にだけ行う
- 取引先の利用者には、照合そのものを行わない（応答の速さの違いからも推測させない）
- 注意の文言に **一致した語そのものを含めない**（画面に出すのは「エンド企業名・単価らしき語が含まれています」まで。本人は自分で書いた文なので、どこかは読めば分かる）
- 照合の結果を **監査ログや応答本文に残さない**（後から一致の有無を引ける経路を作らない）

## 4. 照合の中身

| 対象 | 照合の仕方 | 出典 |
|---|---|---|
| エンド企業名 | このスレッドの対象案件（案件スレッド）、または相手社に公開中の案件（企業スレッド）の `end_client_name` と、本文の部分一致（全角半角・大文字小文字・空白を正規化） | `projects.end_client_name`（🔴 内部限定の列。応答に出さない） |
| 単価らしき語 | 「万円」「円/月」「単価」と数字の組み合わせ（正規表現） | 固定のパターン |

- 🔴 **AI を使わない**（`CLAUDE.md` §3.2「単価とエンド企業名を LLM に渡さない」）
- 照合はサーバ側（`POST /api/threads/{id}/messages` の手前の検査 API）で行い、`end_client_name` をクライアントに渡さない
- 短すぎる名前（2 文字以下）は誤検知が多いので対象外にする（例: 「AB」）

## 5. 画面（`S-031`）

1. ホストの営業が送信（Enter / ボタン）を押す
2. サーバの照合で一致があれば、送信せずに入力欄の上に注意を出す
   - 文言: 「エンド企業名・単価らしき語が含まれています。このスレッドの相手（◯◯社）に表示されます。このまま送信しますか？」
   - ボタン: 「このまま送信」/「書き直す」
3. 「このまま送信」で送る。「書き直す」で入力欄に戻る（本文は消さない）
4. 一致が無ければ、注意を出さずにそのまま送る

## 6. API（`docs/05` §6.5 の変更案）

| 変更 | 中身 |
|---|---|
| 新規 `POST /api/threads/{id}/messages/precheck` | 本文を受け取り `{ warn: boolean }` だけを返す。🔴 一致した語・件数・種類を返さない。取引先の利用者には常に `{ warn: false }`（照合しない） |
| #51 `POST /api/threads/{id}/messages` | 変更なし（注意を見たうえで送るかは画面の判断。サーバは止めない） |

## 7. テスト

| 種類 | 確かめること |
|---|---|
| 分離テスト | 🔴 取引先の利用者が precheck を何度呼んでも、エンド企業名の有無で応答が変わらない（常に `warn: false`） |
| 単体 | 正規化（全角半角・空白）、短い名前の除外、単価パターン |
| render | 注意の文言に一致した語が含まれない |
| E2E | ホストがエンド企業名を含む文を送ろうとすると注意が出て、「このまま送信」で送れる |

## 8. 決めること（Open Questions）

- 注意を出す対象に「他社名（別の取引先の社名）」も含めるか（含めるとホストの取引先一覧との照合になる）
- 企業スレッドで照合する案件の範囲（相手社に公開中の案件すべて / 直近のものだけ）
- 注意を何回出したかを、運営者向けの指標として件数だけ残すか（内容は残さない）
