## 2. 🔴 境界の注意が特に要るもの

| # | 起きうる事故 | 設計の線 |
|---|---|---|
| 22 一斉案内 | 🔴 **他にどの会社へ案内したかが漏れる**（パートナー同士の相互参照は `CLAUDE.md` §3.1 の最大の事故） | 取引先ごとに**別のスレッドの別の発言**として作る（宛先の一覧を 1 つの行に持たない）。案内できるのは**その取引先に公開済みの案件だけ**（未公開なら案内と同時に公開の手続き = ゲートを通す）。分離テストで「A1 の応答に A2 の存在が 0 件」を固定 |
| 16 社内メモ | 🔴 **単価・エンド企業名を書いたメモが取引先に見える** | メモは `messages` に混ぜず**別の表**にし、RLS を **C2 HOST_ONLY**（ホストだけ）にする。パートナーの読み取りポリシーを 1 つも書かない（`extension_reviews` と同じ）。画面も会話の列と分ける（同じ吹き出しの形にしない） |
| 20・21 お知らせ | お知らせの文面に、相手に出してはいけない項目（単価・エンド企業名・`ExtensionReview` の中身）が混ざる | 文面は**経路 2・5 で既に相手に見えている項目だけ**で組む（`thread-origin-proposal.md` §2 と同じ線）。単価の交渉の中身は人が書く |
| 24 返信の速さ | 取引先の比較が取引先に見える（他社の存在・件数の示唆） | **ホストにだけ**出す。取引先には何も出さない。計算は自社が参加しているスレッドの発言時刻だけ（本文は読まない） |
| 17 AI 要約 | 本文に含まれる氏名・単価が LLM に送られる | `CLAUDE.md` §12 のロールの追加（人間の承認）。§3.2 のマスキングを必ず通す。単価・エンド企業名を渡さない仕組みが要る |
| 7 自動表示 | — | 既存の API（#50）を一定間隔で呼ぶだけなら境界は変わらない。方式（ポーリング / SSE）の決定が要る |
