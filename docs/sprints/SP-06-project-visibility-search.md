## 1. 目的

案件の登録・**公開範囲（越境経路 1）**・案件検索・エンジニアの複合検索を通す。本スプリントの中核は 2 つある。

1. 🔴 **商流情報（エンド企業名・内部単価）を、公開範囲に含まれる相手の画面・エクスポート・通知のいずれにも出さない**（`F-013 AC-2` / `F-014 AC-3`）。**取得後に隠すのではなく、取得時の射影で分ける。**
2. 🔴 **Phase 1 の検索の並び順が決定的であること**（`F-009 AC-1` / `AC-2`）。**スコア・順位・重みに相当する表示項目を Phase 1 に置かない**（スコアは Phase 2 の `F-029`）。

> ⚠️ **`F-014 AC-3`（ゲート FAIL なら公開しない）の検証は SP-07（T-07-09）で行う。** 本スプリントでは公開範囲 API がゲートを呼ぶ**接続点**まで実装し、ゲート本体は SP-07 で入る。**この依存を放置しない** — SP-07 の完了判定に `F-014 AC-3` を含める。

## 4. タスク詳細

### T-06-01 案件の登録・編集（M）

- **実装**: `POST /api/projects` / `PATCH /api/projects/{id}`（#26）。画面は `S-012`（Tier 3）。
- 🔴 **要件を「必須」「尚可」に切り分けて登録する**（`F-013 AC-1`）。`ProjectRequirement.kind` の 2 区分は SP-02 で作成済み。**`F-020` の整合層と `F-029` の足切りが区分を参照できること**をここで担保する。
- 案件の状態（募集中 / 充足 / 後任募集）を持つ。**後任募集は `F-045`（SP-16）から自動生成されうる**ため、`originAssignmentId` を受け入れる形にしておく。
- 作成・更新を `AuditLog` に記録。
- **完了の判定**: `F-013 AC-1` の結合テスト（区分ごとに取得できる）。

### T-06-02 案件詳細と商流情報の射影（L）

- **実装**: `GET /api/projects/{id}`（#27）。画面は `S-011`（Tier 2）。
- 🔴 **応答の型を `HostProjectDetailView` と `PartnerProjectDetailView` に分ける。** `PartnerProjectDetailView` に **`endClientName` / `internalUnitPrice` のフィールドが存在しない**（`undefined` で返すのではなく、型が違う。`docs/05` §4.8 と同じ思想）。
- 🔴 **公開範囲外のパートナーには 404**（403 と区別しない。`docs/04` §10.1 の `S-011`）。パートナー側の空状態は「この案件は現在御社に公開されていません」（404 ページにしない）。
- 案件詳細の閲覧を `AuditLog` に記録（`F-013 AC-3` / `BR-27`）。
- **完了の判定**: `F-013 AC-2` / `AC-3` の結合テスト + **型テスト**（`PartnerProjectDetailView` に商流フィールドが無い）。

### T-06-03 案件の検索と一覧（M）

- **実装**: `GET /api/projects`（#25）。画面は `S-010`（Tier 2）。
- 🔴 **パートナーの母集団は「自社に公開された案件」のみ**（C4 が絞る）。**総件数の表示も同じ母集団から算出する**（`F-015 AC-1`）。
- **並び順は決定的**（更新日時・開始日。`F-015 AC-3`）。
- **性能目標**: 案件 1 万件で p95 1 秒（`F-015 AC-2`）。**判定は SP-12 の負荷テスト**（T-12-02）。本タスクではインデックスと実行計画の確認まで。
- **完了の判定**: `F-015 AC-1` / `AC-3` の結合テスト。

### T-06-04 エンジニアの複合検索と決定的順序（L）

- **実装**: `GET /api/engineers`（#15）の検索条件評価。画面は `S-005`（Tier 2）。
- **検索条件**: スキル（複数・AND / OR）、経験年数、単価レンジ、稼働可能時期、勤務地・リモート可否、所属区分、稼働状況、フリーワード。加えて絞り込みチェックボックス **「開始日に間に合う人だけ」「通勤可能な人だけ」**。
- 🔴 **Phase 1 の並び順は、検索条件への適合と更新日時による決定的な順序。「重み」という概念を持たない**（`F-009 AC-1`）。
- 🔴 **Phase 1 の検索結果に、スコア・順位・重みに相当する表示項目が存在しない**（`F-009 AC-2`）。**画面に重み設定を置かない**（`F-030 AC-4`。`S-040` は Phase 2）。
- 🔴 **絞り込みチェックボックスは既定オフ。** オフのときは開始日が遅い候補・勤務地が合わない候補も一覧に現れる（`F-009 AC-5` / `docs/02` A-03）。
- 🔴 **パートナーが実行した検索の結果に、他パートナーのエンジニアおよび匿名候補が 1 件も含まれない**（`F-009 AC-3` / `BR-56`）。
- **匿名候補の混在は SP-08 で追加する**（`AnonymousCandidateView`）。本タスクでは `OwnEngineerView` のみ。
- **ブロッカーではないが確認中**: [Issue #3](https://github.com/Festal-KM/SES-Platform/issues/3)（開始日の遅れ・勤務地不一致を減点か除外か）。**Phase 1 は「減点」の概念自体が無いため影響しない。** 既定は「一覧には出しつつ明示的なフィルタで絞る」（`docs/02` A-03 / `docs/dev-plan.md` §9）。
- **完了の判定**: `F-009 AC-1`〜`AC-3` / `AC-5` の結合テスト（**同一条件を 10 回実行して並び順が一致する**）。

### T-06-05 検索基盤の実装を 1 箇所に閉じる（L）

- **実装**: 🔴 **日本語全文検索の実装を `packages/db/src/search/*.ts` の 1 箇所に閉じる**（`docs/05` TBD-8）。`pg_trgm` の GIN で代替できる形にしておく。
- **インデックス設計**（`docs/03` §3.7.2）: 🔴 **複合インデックスは `tenant_id` を必ず先頭列に置く**（RLS のポリシー式が等値比較で枝刈りできるようにする）。
- 🔴 **匿名候補が混在する検索を含めて評価する**（`docs/02` `tech-selection` 申し送り 3）。SP-08 で「自社スコープ」「共有スコープ」の**2 本のクエリに分けてアプリ層で決定的にマージ**するため（`docs/03` `program-design` 申し送り 18）、本タスクのインタフェースはその形を前提に設計する。
- **T-01-02 の拡張可否の検証結果**（E-12）を反映する。`pg_bigm` / `pgroonga` が使えない場合は `pg_trgm` のみで組む。
- **完了の判定**: `packages/db/src/search/**` 以外に検索 SQL が現れないことの静的テスト。`EXPLAIN` でインデックスが使われることの結合テスト。

### T-06-06 案件の公開範囲設定（経路 1）（L）

- **実装**: `PUT /api/projects/{id}/visibility`（#28）。画面は `S-013`（Tier 3）。
- 🔴 **公開先を明示的に選択する。既定は誰にも公開されない。「全公開」を既定値として持たない**（`F-014 AC-2`。テナント作成時の既定値は `F-001 AC-1` で設定済み）。
- 🔴 **公開時に品質ゲート（`F-020`）を実行し、PII 層・商流層で FAIL したら公開しない**（`F-014 AC-3`）。**本スプリントでは呼び出しの接続点まで。ゲート本体と AC-3 の検証は SP-07（T-07-09）。**
- 🔴 **越境の根拠は `ProjectVisibility` の行の有無だけ**（`docs/05` §4.4 C4）。**アプリの `if` に越境の判断を書かない。**
- 🔴 **公開範囲に含まれないパートナーの画面・検索・件数・通知のいずれにも、その案件が現れない**（`F-014 AC-1`）。
- **完了の判定**: `F-014 AC-1` / `AC-2` の結合テスト。ゲート接続点のスタブが `PENDING_GATE` として公開を保留すること。

### T-06-07 公開範囲の監査と公開解除の挙動（M）

- **実装**: 公開範囲の変更を **実施者・変更前後の公開先とともに** `AuditLog` に記録する（`F-014 AC-5` / `BR-27`）。
- **公開解除時**: 対象パートナーの一覧からその案件が消える。🔴 **作成済みの提案は残る**（`F-014` 処理④）。`ProjectVisibility.revokedAt` で表す（RLS の C4 が `revoked_at IS NULL` を見る）。
- **完了の判定**: `F-014 AC-5` の結合テスト + 解除後にパートナーの一覧・検索・件数から消え、既存 `Proposal` は残ることの結合テスト。

### T-06-08 パートナーの案件母集団（C4）の検証（M）

- **実装**: SP-02 の C4 ポリシーが、案件の実データで期待どおり効くことを検証する。
- 🔴 **公開先パートナーは、同じ案件に公開されている他のパートナーの社名・件数を知る手段を持たない**（`F-014 AC-4` / `BR-07`）。
  - 案件詳細の応答型に `visibilities` / `visibleToCount` に相当するフィールドを**パートナー向けには持たせない**。
  - 一覧の `total` は自社に公開された案件のみから算出する。
- **完了の判定**: `F-014 AC-4` の結合テスト（2 パートナーに公開した案件で、A 社の応答に B 社の存在が 0 件）。

### T-06-09 「見えない = 存在しない」の API 契約の適用と E2E（M）

- **実装**: `docs/05` §4.8 の表を、本スプリントで追加した全ルート（#25〜#28 / #15 / #17）に適用する。
- **検証項目**: ①境界外の ID は **404**（403 と区別しない）②一覧の `total` は境界適用後の `COUNT` ③**並び順に「全体件数」「順位」を持ち込まない** ④集計・通知・エクスポートも同じ ⑤🔴 **「他にも案件があります」「あなたは N 番目」に相当するフィールドを型に持たない**。
- **E2E**: `docs/05` §17.3 #2 の案件部分（パートナーの全画面・API・集計・通知に他社由来の値が 0 件。**件数バッジ・並び順の変化・示唆も 0 件**）。
- **完了の判定**: E2E #2（案件部分）が green。型テストで禁止フィールドが存在しないこと。
