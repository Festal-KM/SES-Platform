## 1. 目的

3 つを成立させる。

1. 🔴 **利用量の計測を Phase 1 で完成させる**（`BR-43` / `CLAUDE.md` §10.6）。**後から遡って計測できない。** 金額と件数を**独立に**持つ（[Issue #12](https://github.com/Festal-KM/SES-Platform/issues/12)）。
2. 🔴 **`demo` と `sandbox` を Phase 1 時点で成立させる**（`docs/02` 章 1.4）。特に **`sandbox` には本番と同じ統制（分離・記録・暗号化・保持期間）が効いていること**（`BR-62`）。
3. 🔴 **`sandbox` に投入された実在するエンジニアの経歴を、期限到来で確実に削除できる状態を作る**（`F-064`）。**これはスコープではなく統制の問題である** — 削除の仕組みが無いまま期限切れテナントを抱えると、**第三者の個人情報を削除手段のないまま保持する**ことになる。

### T-10-03 上限到達の判定と停止（L）

- **実装**: `F-027` 処理①〜⑤。`docs/02` 章 7.5 / 章 7.7 / `docs/03` `ui-design` 申し送り 6・12。
- 🔴 **3 種類を区別して扱う**（同じ表示にしない）:
  1. **AI コスト上限** — **1 日単位。停止する。** 到達すると **`gate-inspector` も停止する**（SP-07 の HELD）。
  2. **AI クォータ超過** — **月単位。停止せず従量課金に移行する。**
  3. **ストレージ上限** — **超過でアップロードが停止する**（従量へ移行しない）。
- **メールは日次・分次の両方を判定し、分次超過は待機、日次超過は停止として区別する**（`F-027 AC-2`。SP-04 で実装済みの上限を表示に接続する）。
- 🔴 **上限接近（既定 80%）でテナント管理者と `F-057` に通知する**（`F-027 AC-4`）。**Phase 1 の通知手段はアプリ内表示とメール送信**（宛先は自テナントの管理者 = 分類 1 のため `sandbox` では実送信）。
- 🔴 **AI の日次コスト上限に到達した状態で AI 機能を起動すると、実行されず「上限に達したため停止中」と停止理由が実行者に表示される。エラーコードのみの無言停止にならない**（`F-027 AC-1` / `BR-24`）。
- 🔴 **残量・上限値はホスト所属ロールにのみ表示し、パートナー所属ロールには停止の事実と理由のみ**（`F-027 AC-1` / `BR-04` の第二境界）。`GET /api/usage/blocked-notice`（#70）がパートナー向け。
- 上限到達・停止・解除を `AuditLog` に記録する。
- **完了の判定**: `F-027 AC-1`〜`AC-4` の結合テスト（3 種の挙動差を含む）。

### T-10-09 🔴 削除（`CLOSING` → `PURGED`）と返却 CSV（L）

### T-10-12 🔴 削除予告（`tenant.closing-notify`）と配送確認（M）

- **実装**: ジョブ **`tenant.closing-notify`**（毎日 02:08 JST。`docs/05` §9.7）と、**`tenant.purge-scan` の配送済み条件**。`docs/02` `F-064 AC-10` / 章 7.7-④ / `A-005` 項目 15（表示は SP-11 の T-11-04）。
- 🔴 **`retention.notify`（`F-046`。Phase 2）/ `tenant.sandbox-notify`（`F-054 AC-9`。T-10-08）とは別物である。** 本ジョブは **`CLOSING → PURGED` の削除予告**であり、3 つを 1 つにまとめない（対象・期日・宛先の意味が違う）。
- **対象と段**: `lifecycleState='CLOSING'` のテナントの `OWNER` / `ADMIN`（`SANDBOX` 由来なら見込み客 = `OWNER`）。2 段 — `phase='ENTERED'`（`closingEnteredAt <= today`。**削除予定日を明記**）/ `phase='D7'`（`closingEnteredAt + 23日 <= today`）。
- 🔴 **各段の起票条件は「期限を過ぎ、かつ未処理」**（日付一致にしない）。「未処理」= 当該 `(tenantId, phase)` に `status IN ('QUEUED','HELD_PROVIDER_QUOTA','SENT','MOCKED')` の `EmailDispatch` 行が無いこと。`EmailDispatch(templateKey='TENANT_CLOSING_NOTICE', dedupeKey='TENANT_CLOSING_NOTICE:{tenantId}:{phase}:{yyyymmdd}:{recipientHash}')` を作成して `email.dispatch` を enqueue する（**分類 1 = `sandbox` でも実送信**）。
- **不達時**: `FAILED`（宛先全員バウンス等）なら**翌日に再起票**（`dedupeKey` に日付を含むため `UNIQUE` に当たらない）し、`A-005` 項目 15 に `cause='NOTICE_UNDELIVERED'` で出す。
- 🔴 **`tenant.purge-scan` の enqueue 条件に「予告が配送済み」を加える**（`F-064 AC-10`）: `email_dispatches(tenantId, templateKey='TENANT_CLOSING_NOTICE')` に **`status IN ('SENT','MOCKED')` の行が 1 件以上あり、かつ `status IN ('QUEUED','HELD_PROVIDER_QUOTA')` の行が 0 件**であること。🔴 **`QUEUED` / `HELD_PROVIDER_QUOTA` の間は enqueue せず次回へ持ち越す** — **上限到達を理由に予告を省いて削除に進む経路を作らない**（`docs/02` 章 7.7-④）。
- 🔴 **`MOCKED` を配送済みとみなすのは、送信系が全てモックの `development` / `demo` に限る。** `sandbox` の `TENANT_CLOSING_NOTICE` は分類 1 であり実送信されるため `MOCKED` にならない（**`docs/05` §13.2 の「疑似送信の記録」を配送済みの根拠にしない**）。
- **未配送のテナントは満了後も残る**ため、`A-005` 項目 15 に `cause='NOTICE_PENDING'`（予告行が 1 件も無い場合を含む）/ `'NOTICE_UNDELIVERED'` を区別して出す（件数・状態・`overdueDays` のみ。`BR-40`）。🔴 **削除ジョブの失敗（`TenantPurgeRun.status='FAILED'` = `A-005` 項目 7）とは別行**（`F-059 AC-2`「失敗と保留・完了を混ぜない」）。**失敗ジョブ数に加算しない。**
- **完了の判定**: `F-064 AC-10` の結合テスト（①2 段の予告が「期限を過ぎ、かつ未処理」で 1 回ずつ起票される ②`FAILED` なら翌日に再起票される ③`QUEUED` / `HELD_PROVIDER_QUOTA` が残っている間は `tenant.purge` が enqueue されない ④`SENT` になって初めて enqueue される ⑤`sandbox` 相当で `MOCKED` を配送済みとみなさない）+ 🔴 **E2E #24**（`docs/05` §17.3。`MAIL_PROVIDER_DAILY_QUOTA=1` で予告が `HELD_PROVIDER_QUOTA` のまま `closingEnteredAt + 30日` を過ぎても `TenantPurgeRun` 0 件・個人情報が残る・`A-005` に `kind='PURGE_NOTICE_PENDING'` / `cause='NOTICE_PENDING'` / `overdueDays >= 0` が出て `PURGE_JOB_FAILED` は 0 件 → `now` を 24h 進めて `send.hold-release` → 予告が `SENT` → 翌 `tenant.purge-scan` で初めて `PURGED`。**`tenant.purge` を直接 enqueue しても配送未確認なら no-op**）。
