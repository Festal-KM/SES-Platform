## 見るべきポイント

記入例を読むとき、以下に注目すると効果が高い。

### 1. §1.1「解決する課題」の粒度

「面倒だから」で止めず、**どの工程が形骸化し、その結果どうなるか**まで書かれている。ここが弱いと、生成される `docs/01` が「機能の羅列」になる。

### 2. §3「ハードルール」の書き方

1 件ごとに以下が揃っていることを確認する：

- 違反が一意に判定できる書き方になっているか
- **破れない担保**（Lint / DB 制約 / 型 / 実行時ガード）まで書かれているか
- **なぜ事故なのか**が 1 行添えられているか
- 例外があるなら**射程**が明示されているか

### 3. §4.2 のステートマシン

- **「上図がこのステートマシンの全体である」と明記されている**こと
- **保留と失敗が別の状態**になっていること
- 自動リトライを禁じる遷移が明示されていること

### 4. §5 の成功条件

「基盤ができている」ではなく、**テストで判定できる文**になっていること。

### 5. §7 の事故指標

`**0 件**（許容しない）` の行があること。**この 1 行が `code-reviewer` の厳しさを決める**。

### 6. 該当しない章の書き方

`§13 マルチデバイス対応` が「本プロジェクトでは該当なし。」の 1 行になっていることを確認する。

🔴 **章そのものを削除していない**点が重要。`.claude/agents/*.md` は章番号を参照する契約で書かれているため、番号を詰めると全エージェントの参照がずれる。

## 🔴 注意

この記入例は**架空のプロダクト**であり、そのままコピーして使うものではない。

自分のプロダクトの `CLAUDE.md` は、[`prompts/00-project-brief.md`](../prompts/00-project-brief.md) のブリーフを書いてから `/kickoff` で埋めるのが最も精度が高い。
