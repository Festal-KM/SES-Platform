# 02. 実装フェーズ — `/iterate` でタスクを消化する

設計フェーズが `## PHASE_COMPLETE` になってから始める。

---

## 🔴 大原則

```
/iterate T-01-03      ← 1 タスク = 1 回
```

`/iterate` は **programmer → code-reviewer → e2e-tester** を「APPROVED かつ PASS」まで**最大 5 周**繰り返す。

- 🔴 **複数タスクをまとめて渡さない。** `/iterate T-01-01 と T-01-02 を実装して` は精度が落ちる
- 🔴 **設計フェーズが終わっていない状態で始めない。** `programmer` は `docs/05` を実装の根拠にする
- 5 周で通らなければ `ESCALATE` して人間判断に委ねる

---

## 基本の使い方

### タスク ID を渡す

```
/iterate T-01-03
```

`programmer` が `docs/sprints/SP-01-*.md` から該当タスクの詳細を読む。**最も精度が高い渡し方**。

### 自然言語で渡す

```
/iterate ログイン画面のバリデーションエラーを、フィールド直下に表示するよう修正して
```

タスク化されていない小さな修正に使う。この場合、**指示文そのものが仕様として扱われる**ので、受け入れ基準まで書くとよい：

```
/iterate ログイン画面のバリデーションエラーをフィールド直下に表示する。
受け入れ基準:
- メールアドレス形式エラーが該当フィールドの直下に赤字で出る
- 複数フィールドが同時にエラーの場合、それぞれの直下に出る
- 画面上部のサマリエラーは廃止する
```

---

## Phase 0 の最初のタスクは特別扱いする

**リポジトリがまだ空の状態**では、`programmer` が参照する既存パターンが無い。最初の 1〜2 タスクは、こう補強する：

```
/iterate T-00-01

補足:
- これはリポジトリ最初のタスクです。既存パターンはありません
- docs/05-program-design.md のディレクトリ構成に厳密に従ってください
- 新規依存の追加は宣言のみで、インストールは実行しないでください
```

---

## 🔴 ハードルールに触れるタスクは明示する

`/iterate` は `code-reviewer` に「タスクが `CLAUDE.md` §3 のどのハードルールに触れるか」を渡すが、**判定を助けると精度が上がる**：

```
/iterate T-02-05

このタスクは CLAUDE.md §3.4（冪等性）と §3.1（データ分離）に触れます。
特に外部送信ジョブの CAS 順序を重点的にレビューしてください。
```

これを書かないと、`code-reviewer` が該当項目を `N/A` にしてしまうことがある。

---

## 各段階で何が起きるか

| 段階 | 誰が | 何を | 終端 |
|---|---|---|---|
| Step 1 | `programmer` | 実装 + ユニットテスト | `## DONE` / `## BLOCKED` |
| Step 2 | `code-reviewer` | 21 項目のチェックリスト | `## APPROVED` / `## REQUEST_CHANGES` / `## ESCALATE` |
| Step 3 | `e2e-tester` | E2E テスト作成・実行 | `## DONE` / `## BLOCKED` |

- Step 2 が `REQUEST_CHANGES` → Step 1 に戻る（**E2E までは進めない**）
- Step 3 が `BLOCKED` → Step 1 に戻る。**次周は Step 2 も必ず再実行される**

---

## 進行中に確認すること

### ✅ 見るべきもの

- **`code-reviewer` の Findings で `NG` が付いた項目**。何が問題だったかは学びになる
- **`N/A` の理由**。`CLAUDE.md` §3 に該当ルールがあるのに `N/A` になっていたら、指摘を追加する
- **`e2e-tester` が報告する外部 API モックの呼び出し回数**。冪等性の検証はここに出る

### 🔴 危険信号

| 症状 | 意味 | 対処 |
|---|---|---|
| `code-reviewer` が毎回 `APPROVED` を即返す | §3 が薄く、照合基準が無い | `CLAUDE.md` §3 と §7 を見直す |
| 同じ指摘で 3 周以上ループ | `docs/05` の設計自体に問題がある | ループを止め、`program-design` を `/design-iterate` で直す |
| `programmer` が設計外のファイルを作る | `docs/05` のディレクトリ構成が不十分 | `docs/05` に置き場所を追記する |
| E2E が毎回タイムアウト | ジョブワーカーが起動していない | 起動手順を `docs/05` §テスト戦略に明記する |
| 🔴 実 API を叩いた形跡がある | **即停止**。不可逆な事故になり得る | ループを止め、モック設定を確認する |

---

## `ESCALATE` が返ったとき

5 周で通らなかった場合の出力：

```
## /iterate ESCALATED
- Task: ...
- Last code-reviewer verdict: ...
- Last e2e-tester result: ...
- 推奨される次の一手: ...
```

**判断は人間がする**（`CLAUDE.md` §8.6）。よくある原因と対処：

| 原因 | 対処 |
|---|---|
| タスクが大きすぎる | `pm` で再分解する。「1 タスク = 1 `/iterate`」の粒度に戻す |
| `docs/05` の API 仕様が機能要件を満たしていない | `/design-iterate program-design` で設計を直してから再実装 |
| ハードルールが矛盾している | `CLAUDE.md` §3 を人間が直す（§8.6） |
| 環境不備（DB 未起動・ワーカー未起動） | 環境を整えてから再実行 |

## よくある質問

**Q. `/iterate` を使わず直接 `programmer` を呼んでもよいか**
A. 可能だが**推奨しない**。レビューと E2E が走らないため、`CLAUDE.md` §3 の違反が素通りする。急ぎの調査やプロトタイプ限定にする。

**Q. E2E が不要なタスク（型定義の追加など）はどうなるか**
A. `e2e-tester` が「新規 spec 不要」と判断し、既存スイートが緑であることを確認して `## DONE` を返す。勝手に無意味な spec を書かない仕様になっている。

**Q. テストを通すためにプロダクトコードを直してよいか**
A. `e2e-tester` はそれを禁止されている。プロダクト側の修正が必要なら `## BLOCKED` で `programmer` に差し戻す。

**Q. 新しい依存パッケージを入れたい**
A. `programmer` はマニフェストを編集するだけで、インストールは実行しない（ユーザー承認事項）。報告に「次のステップ: インストール」と書かれるので、人間が実行する。
