# 03. 仕様の追加・変更が発生したとき

🔴 **仕様が変わったら、その場で上流ドキュメントを更新する。** 実装や下流ドキュメントに手をつける前に行う。

---

## なぜ「その場で」なのか

このハーネスの全エージェントは、**上流ドキュメントを唯一の入力として動く**。

- **エージェントはチャット履歴を読まない。** あなたと AI がチャットで合意した仕様は、次のエージェント起動時には存在しない
- **上流が古いまま下流を進めると、以降のすべてのエージェントが誤った前提で作業する。** 気づいたときには広範囲のやり直しになる
- **設計書が実態と乖離した時点で、この構成は機能しなくなる**

「後でまとめて更新する」は**必ず漏れる**。

---

## 手順

### Step 1: 変更がどの層の話かを見極める

| 変更の種類 | 起点となるドキュメント |
|---|---|
| プロダクト方針・ハードルール・技術スタック・環境構成 | `CLAUDE.md` |
| 業務価値・業務フロー・ビジネスルール (`BR-xx`) | `docs/01` |
| 機能・受け入れ基準・非機能要件 (`F-xxx` / `UC-xx`) | `docs/02` |
| 技術選定・外部 API 仕様・コスト | `docs/03` |
| 画面・UI 挙動 (`S-xxx` / `A-xxx`) | `docs/04` |
| DB・API・ジョブ・モジュール設計 | `docs/05` |
| スプリント・タスク | `docs/dev-plan.md` / `docs/sprints/` |

### Step 2: 起点の層と、それより下流をすべて更新する

🔴 **下流だけ直して上流を放置するのが最も避けるべき状態。** 次にエージェントを回した瞬間、上流の古い記述で上書きされる。

### Step 3: 影響する ID を洗い出す

`F-xxx` / `S-xxx` / `A-xxx` / `BR-xx` / `UC-xx` を確認する。

🔴 **ID は削除せず欠番にする。** 参照の安定性を保つため（`CLAUDE.md` §8.8）。

### Step 4: 整合性を再検証する

影響を受けた各ドキュメントに `/design-iterate <エージェント名>` をかける。

### Step 5: 実装済みなら差分タスクを追加する

すでに実装が進んでいる場合、影響タスクを `docs/sprints/` に追加する。実装済みコードとの差分を放置しない。

## そのまま貼れる指示文

### パターン A: 機能要件レベルの変更

```
仕様変更が発生しました。CLAUDE.md §8.7 の手順に従って反映してください。

【変更内容】
{{何がどう変わるか}}

【変更の理由】
{{なぜ変えるか。この理由は下流の判断に使われるので必ず書く}}

【対応】
1. まず影響範囲を報告してください:
   - 起点となるドキュメント
   - 影響する ID の一覧 (F-xxx / S-xxx / A-xxx / BR-xx / UC-xx)
   - 実装済みコードへの影響の有無
2. 私が確認したら、上流から順に更新してください
3. ID は削除せず欠番にしてください

🔴 まず影響範囲の報告だけしてください。私の確認前にドキュメントを書き換えないでください。
```

**「まず影響範囲だけ報告」を入れる理由**: 変更の波及が想定より大きいことがよくある。波及範囲を見てから「やらない」判断に戻れるようにする。

### パターン B: ハードルールの追加・変更

🔴 **`CLAUDE.md` の改訂は人間の承認事項**（§8.6）。エージェントに勝手に書き換えさせない。

```
CLAUDE.md §3 にハードルールを追加したいと考えています。

【追加したいルール（案）】
{{ルールの案}}

【背景】
{{なぜ必要か。どんな事故を防ぎたいか}}

以下を検討して報告してください。まだ CLAUDE.md は書き換えないでください:
1. このルールは CLAUDE.md §0 の「良いハードルールの条件」を満たしているか
   - 違反が一意に判定できるか
   - 破れない担保（型 / DB 制約 / Lint / 実行時ガード）まで書けるか
   - なぜ事故なのかの理由が 1 行あるか
   - 例外があるなら射程が明示されているか
2. 満たしていない場合、どう書き直すべきか
3. 既存のハードルールと矛盾しないか
4. 既存の実装コードでこのルールに違反している箇所はあるか
5. 影響を受ける docs/01〜05 と、追加が必要なタスク
```

### パターン C: スコープを削る（機能を落とす）

```
{{機能名}} を Phase 1 のスコープから外します。

【理由】
{{なぜ落とすか}}

【対応】
1. CLAUDE.md §6「対象外」に理由付きで追記する案を提示してください
   （CLAUDE.md 自体は私が確認してから更新します）
2. docs/02 の該当 F-xxx を「Phase 2 以降」に移動し、ID は欠番にせず残してください
3. docs/04 の該当画面の扱い（削除 / 非表示 / Phase 2 送り）を提案してください
4. docs/dev-plan.md と docs/sprints/ から該当タスクを外してください
5. 実装済みのコードがある場合、削除するか残すかを提案してください

🔴 理由を必ず docs に残してください。理由の無い「やらない」は後で実装されてきます。
```

### パターン D: 外部 API の仕様が変わっていた

```
{{サービス名}} の {{仕様項目。例: レート上限}} が docs/03 の記述と違っていました。

【現在の docs/03 の記述】
{{...}}

【実際の値】
{{...}}（出典: {{URL}}）

【対応】
1. tech-selection エージェントで docs/03 を更新してください（出典 URL を必ず残す）
2. この値に依存している設計を docs/05 から洗い出してください
   特に、レート制限・コスト上限のガード値
3. 実装済みのガード値があれば、修正タスクを docs/sprints/ に追加してください

🔴 CLAUDE.md §3 にこの数値がハードルールとして書かれている場合、
CLAUDE.md の改訂案として提示してください（私が確認します）。
```

---

## やってはいけないこと

| やってはいけない | なぜ |
|---|---|
| 「後でまとめて更新する」 | 必ず漏れる。変更が決まった時点で反映する |
| チャットでだけ決めて文書化しない | エージェントはチャット履歴を読まない。**書かれていない決定は存在しない** |
| 下流ドキュメントやコードにだけ反映する | 次にエージェントを回した瞬間、上流の古い記述で上書きされる |
| `CLAUDE.md` をエージェントに書き換えさせる | 全エージェントの一次資料。改訂は人間の承認事項（§8.6） |
| ID を削除する | 参照が壊れる。欠番にする（§8.8） |

---

## チェックリスト

仕様変更の反映が終わったら：

- [ ] 起点の層より下流のドキュメントをすべて更新した
- [ ] 影響する ID を洗い出した。削除せず欠番にした
- [ ] 更新したドキュメントに `/design-iterate` をかけて APPROVED を得た
- [ ] 実装済みコードへの差分タスクを `docs/sprints/` に追加した
- [ ] `CLAUDE.md` の改訂が必要な場合、人間が確認して反映した
