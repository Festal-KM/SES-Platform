# 04. 完了確認 — スプリント / フェーズの区切り

`pm` エージェントを**完了確認モード**で起動する。プロンプト冒頭に `MODE: REVIEW` を書くことでモードが切り替わる。

---

## 基本形

```
MODE: REVIEW
TARGET: SP-01

pm エージェントで完了確認をしてください。
```

`TARGET` に指定できるもの：

| TARGET | 対象 |
|---|---|
| `SP-01` | スプリント 1 |
| `設計フェーズ全体` | `docs/01`〜`docs/05` + `dev-plan` + `sprints` |
| `Phase 1` | `CLAUDE.md` §5 の Phase 1 の成功条件 |

---

## 返ってくるもの

| 終端文字列 | 意味 |
|---|---|
| `## PHASE_COMPLETE` | 全項目クリア |
| `## PHASE_INCOMPLETE: N 件` | **1 件でも NG があればこちら** |

🔴 **完了確認モードではドキュメントを書き換えない。** 判定だけを返す。

🔴 **1 件でも NG なら INCOMPLETE。** ここで妥協すると、次フェーズのコストが倍になる。

---

## 何が検査されるか

### 設計フェーズの完了確認

- `docs/01`〜`docs/05`、`dev-plan.md`、`sprints/` が存在し、各エージェント定義が要求する章を満たしているか
- 上流 ID（`BR-xx` → `F-xxx` → `S-xxx` → タスク）が下流で消えていないか
- 各ドキュメントの「後続エージェントへの申し送り」が下流で消費されているか
- 🔴 **`CLAUDE.md` に `{{...}}` の未置換プレースホルダが残っていないこと**（残っていたら**無条件 NG**）
- 🔴 **`CLAUDE.md` §3 のハードルール 1 件ごとに、対応する `BR-xx` が存在すること**

### スプリントの完了確認

- スプリント内の全タスクが完了しているか
- 各タスクの受け入れ基準が満たされているか
- ユニットテスト・E2E が緑か
- `CLAUDE.md` §3 のハードルールに違反する実装が残っていないか

### Phase の完了確認

- `CLAUDE.md` §5 に書かれた**その Phase の成功条件**を満たしているか

🔴 成功条件が「基盤ができている」のような判定不能な文だと、ここで判定できない。その場合 `pm` は成功条件自体の書き直しを要求してくる。

---

## `PHASE_INCOMPLETE` が返ったとき

```
MODE: REVIEW
TARGET: SP-01
```
↓
```
## PHASE_INCOMPLETE: 3 件
1. T-01-04 の受け入れ基準「他テナントのデータが取得できないこと」に対応する
   ユニットテストが存在しない
2. docs/05 §8 に定義された AuditLog への記録が、承認操作で実装されていない
3. docs/02 の F-012 に対応する実装が見当たらない
```

**対処**: 指摘 1 件ごとに `/iterate` を回す。

```
/iterate T-01-04 の受け入れ基準「他テナントのデータが取得できないこと」に対する
ユニットテストを追加する。
pm の完了確認で「テストが存在しない」と指摘されたもの。
```

全件解消したら、**もう一度 `MODE: REVIEW` を回す**。指摘への対応が別の項目を壊していることがある。

---

## いつ完了確認をかけるか

| タイミング | TARGET |
|---|---|
| 設計フェーズの最後（`docs/05` と `dev-plan` 完成後） | `設計フェーズ全体` |
| スプリントの全タスクが `/iterate` を通ったとき | `SP-NN` |
| Phase の全スプリントが完了したとき | `Phase N` |
| 🔴 **本番リリース前** | `Phase N` + 下の追加確認 |

---

## リリース前の追加確認

`pm` の完了確認に加えて、以下を明示的に依頼する。**不可逆な事故に直結する項目**なので、通常のレビューとは別に確認する。

```
MODE: REVIEW
TARGET: Phase 1

加えて、以下をリリース前チェックとして確認してください:

1. CLAUDE.md §7 で「0 件」とされた事故について、
   それを防ぐ実装と、それを検証するテストが両方存在するか
2. production でモック実装が選ばれ得る経路が無いか（CLAUDE.md §11 がある場合）
3. 外部サービスのトークンが、ログ・エラー追跡・LLM プロンプトに
   出ていないこと（Grep で確認）
4. 外部書き込みジョブの max_attempts が 1 になっているか
5. 新規テーブルにデータ分離の機構が有効化されているか（CLAUDE.md §3.1 がある場合）
6. 利用量・コストの計測が漏れなく行われているか
   （後から遡って計測できないため）
```

---

## 完了確認が機能しないとき

| 症状 | 原因 | 対処 |
|---|---|---|
| 毎回 `PHASE_COMPLETE` が即返る | `CLAUDE.md` §5 の成功条件が判定不能 | 成功条件をテスト可能な文に書き直す（§8.6 により人間が判断） |
| 指摘が抽象的で対処できない | 上流ドキュメントの受け入れ基準が曖昧 | `docs/02` の受け入れ基準を `/design-iterate` で具体化する |
| 同じ指摘が解消後も返る | ドキュメントとコードの乖離 | `docs/05` を実装に合わせて更新する（`prompts/03-spec-change.md`） |
| `{{...}}` 未置換で無条件 NG | `CLAUDE.md` の記入漏れ | `/kickoff` を再実行して残りを埋める |
