## 🔴 精度を決める 3 つのこと

このハーネスの出力品質は、**あなたが最初に渡す情報**でほぼ決まる。技術的な工夫より、以下 3 点のほうが効く。

### 1. 「何を作るか」より「なぜ今それが回っていないか」を書く

AI は「作るもの」を書けば作る。しかし**それが正しいものかは判断できない**。判断させるには、現状の業務がなぜ回らないのかを**構造として**渡す必要がある。

- ❌ 「顧客管理システムを作りたい」
- ✅ 「営業が案件状況を Excel で管理していて、更新が属人化している。結果、月次の予実会議で 3 人が別々の数字を持ち寄り、最初の 30 分が数字合わせに消える」

後者だと、AI は「予実の数字が 1 つに定まること」を成功条件として扱える。前者だと機能の羅列しか出てこない。

### 2. 「絶対に起こしてはならない事故」を 1 つ以上書く

これが `CLAUDE.md` §7 と §3 になり、**レビューの厳しさを決める**。

事故が定義されていないと、`code-reviewer` は「特に問題ありません」を返し続ける。逆に「二重投稿は 0 件（許容しない）」と書いてあれば、冪等性の実装を執拗に検査する。

事故の候補：
- 他の顧客のデータが見える
- 同じものが 2 回外部に出る（投稿・送信・請求）
- 未承認のものが公開される
- 本番のつもりでない操作が本番に届く

### 3. 「やらないこと」とその理由を書く

理由の無い「やらない」は、下流のエージェントが**良かれと思って実装してくる**。

- ❌ 「多言語対応はしない」
- ✅ 「多言語対応はしない（理由: 対象顧客が国内の中小企業に限られ、i18n の構造を今入れると画面設計の工数が倍になるため。Phase 4 で再検討）」

## 使い方の原則

- 🔴 **1 度に 1 つのことを頼む**。「docs/01 と docs/02 を作って」は精度が落ちる。1 本ずつ APPROVED まで確定させる。
- 🔴 **チャットで決めたことは必ずドキュメントに落とす**。エージェントはチャット履歴を読まない。**ドキュメントに書かれていない決定は存在しないのと同じ**。
- **分からないことは「分からない」と書く**。特に外部 API の数値（レート上限・単価・無料枠）を推測で埋めると、下流が確定値として扱って事故になる。`CLAUDE.md` §9 に回せば `tech-selection` が公式ドキュメントで裏取りする。
