# recipes/ — ハードルールのレシピ集

`CLAUDE.md` §3「ハードルール」に**そのまま貼れる形**のルール集。

## なぜこれがあるか

このハーネスの精度は **§3 の質**でほぼ決まる。`design-reviewer` と `code-reviewer` は §3 を照合基準として動くため、§3 が曖昧だと**レビューが「それっぽい感想」に劣化する**。

しかし「良いハードルール」は、実際に事故を踏んでからでないと書けないものが多い。ここには、**実プロダクトで踏んだ事故から逆算して書かれたルール**を置いてある。自プロダクトに該当するものをコピーし、語彙を置き換えて §3 に貼る。

## 使い方

1. プロダクトに該当するレシピを開く。
2. **「§3 に貼るハードルール」セクションをコピー**して `CLAUDE.md` の該当節に貼る。
3. `{{...}}` をプロダクトの語彙に置換する。**置換漏れを残さない**（`pm` の完了確認が無条件 NG にする）。
4. 「なぜ事故になるか」は消さずに残す。**理由が無いとエージェントは機械的に拡大解釈する**。

`/kickoff` を使う場合、ラウンド 5 でこの選定を対話的にやってくれる。

## 🔴 コピーするときの注意

- **レシピをそのまま貼らない**。プレースホルダが残ったままだと下流が意味を取れない。
- **該当しないルールを「念のため」貼らない**。守れないルールが §3 にあると、レビューが常時 NG を出し、やがて無視されるようになる。§3 は**全部守れる状態**を維持する。
- **例外を作るなら射程を明示する**。「認証テーブルはこの規律の射程外」と書くなら、**「射程外にできるのはここだけ」まで書く**。例外が 1 つあると、エージェントは類似ケースにも例外を作りたがる。

## レシピを自分で書き足す場合

`CLAUDE.md` §0 の「良いハードルールの条件」を満たすこと：

1. 違反が一意に判定できる
2. 破れない担保（型 / DB 制約 / Lint / 実行時ガード）まで書いてある
3. なぜそれが事故なのかが 1 行ある
4. 例外を作るなら射程が明示されている

加えて、**「静かに壊れる経路」を必ず書く**。良いレシピの価値の大半はここにある。

> 静かに壊れる = **テストは通り、UI も正常に見え、しかし守りたかったものが守られていない**状態。
> このハーネスで最も高くつくのはこれであり、レビュー項目に落とさない限り必ず見逃される。
