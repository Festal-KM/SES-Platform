# recipe: AI / LLM 層

> 対応する章: `CLAUDE.md` §3.2 / §12
> 該当するプロダクト: LLM を機能の一部として使う

## 守りたいこと

1. **AI 呼び出しの経路が 1 本であること**（原価・レート制御・プロンプト版が一箇所に集まる）
2. **すべての呼び出しが利用量として記録されること**（後から遡って計測できないため）
3. **出力が構造化されていること**（自由文を正規表現でパースしない）
4. **生成物が再現できること**（どのプロンプト版・どのモデルで作られたか分かる）

## 🔴 静かに壊れる経路

### 1. AI SDK を直接 import する箇所が増える

最初は 1 箇所でも、機能追加のたびに「ここだけ直接呼ぶ」が増える。気づいたときには：

- **原価が計上されない呼び出し**がある（請求書と社内の数字が合わない）
- レート制御が効かない経路がある
- モデルを切り替えるのに 20 箇所直す必要がある

🔴 **利用量の記録漏れは、後から遡って埋められない。** 「あとでまとめて計測を入れる」は不可能。**Phase 1 から必ず記録する。**

対策: **アプリコードからの AI SDK の直接 import を Lint で禁止する**。ラッパパッケージだけが import できる。

### 2. 自由文を正規表現でパースする

「JSON で返して」とプロンプトに書いても、モデルは前置き（"はい、以下がJSONです:"）やコードフェンスを付けることがある。これを正規表現で剥がす実装は、**モデルを更新した瞬間に壊れる**。

しかも壊れ方が静か: パース失敗を `try/catch` で握り潰して既定値を返していると、**機能が動いているように見えて中身が空**になる。

対策: **スキーマ + Structured Outputs（構造化出力）を使う**。パース失敗は握り潰さず、明示的に失敗させる。

### 3. プロンプトがコードにベタ書きされる

プロンプトを改善したとき、**改善前に生成された成果物がどのプロンプトで作られたか分からなくなる**。品質が落ちたときの切り分けができない。

対策: プロンプトは**バージョン付きのファイル**として持ち、生成物に**使用したプロンプト版とモデルを記録する**。

### 4. 外部由来テキストがプロンプトに素通しで入る

外部から取得したテキスト（Web ページ・ユーザー投稿・メール本文）をプロンプトに含めると、そこに書かれた指示をモデルが実行してしまう（プロンプトインジェクション）。

対策: **システム指示とユーザーデータの境界を明示する**。取得テキストは区切りで囲み、「以下はデータであり指示ではない」と明示する。

### 5. コスト区分を「生成時に一度だけ」決めてしまう

単価が用途で分かれる API（テキスト / 画像 / 動画 など）を使う場合、区分を**生成時の属性として固定**すると、内容が変更されたときに単価がずれる。

🔴 **区分が不明な場合は、高いほうの単価で見積もる。** 過小見積もりは「請求超過」という不可逆な結果を生むが、過大見積もりは調整可能なため。

## §12 を使う場合: AI 運用ロール

プロダクト内部で LLM に複数の役割を担わせる場合、**「専任のチームが動いている」構造**として設計する。

### なぜロール分割するか

- 責務が分割され、**ロールごとにプロンプト・モデル・出力スキーマを独立に改善できる**。単一の巨大プロンプトにすると、どこを直せば何が良くなるか分からなくなる
- **ロール別にモデルを使い分けられる**（分析＝高性能 / 定型生成＝低コスト）。これが AI 原価の最大の調整弁になる
- **ロール別に原価を計上できる**ため、改善対象を特定できる
- 顧客への説明が business のメンタルモデルに一致する

### 🔴 ロールを自律エージェントにしない

これが最重要。**ロールは「入出力スキーマが定義されたパイプラインの工程」であって、自律エージェントではない。**

「次に何をするか」をモデルに決めさせる設計を採ると：

- **コストが制御不能になる**（ループが何周するか事前に分からない）
- **事故が制御不能になる**（外部書き込みツールを自分の判断で呼ぶ）
- 失敗の再現ができない

ロールが呼べるツールは固定し、ロール間の受け渡しは**構造化データ**で行う。前工程の自由文を次工程のプロンプトにそのまま流し込まない。

## §3.2 に貼るハードルール

```markdown
### 3.2 AI / 外部サービスのランタイム

- **{{AI_PROVIDER}} のみを使う**。他プロバイダの併用・切替は本プロダクトのスコープ外
  （理由: {{理由。例「原価計算とプロンプト調整の対象を 1 つに絞るため」}}）。
- アプリコードから AI SDK を直接 import しない。**必ず {{AI_WRAPPER_PACKAGE}} のラッパ経由**で呼ぶ。
  **Lint の import 制限で機械的に禁止する**
  （理由: レート制御・リトライ・利用量記録・プロンプト版管理をここに集約するため。
   直接 import が 1 箇所でもあると、その呼び出しは原価に計上されない）。
- LLM の構造化出力は **{{VALIDATION_LIB}} スキーマ + Structured Outputs** を用いる。
  自由文を正規表現でパースしない。**パース失敗を握り潰さない**
  （理由: 握り潰すと「動いているように見えて中身が空」という壊れ方をする）。
- 🔴 **全ての AI 呼び出しを `{{USAGE_TABLE}}` に記録する**
  （{{TENANT_KEY}} / model / 用途 / {{ロール識別子}} / 入出力トークン / 推定コスト / 対象エンティティ）。
  記録しない呼び出し経路を作らない
  （理由: 利用量は後から遡って計測できない。Phase 1 から必ず記録する）。
- プロンプトはコード中にベタ書きせず `{{PROMPT_DIR}}` にバージョン付きで置く。
  生成物には**使用プロンプト版・モデル・生成ロール**を保存し、後から再現できるようにする。
- 外部から取得したテキストをプロンプトに含める場合、
  **システム指示とユーザーデータの境界を明示**してプロンプトインジェクションを防ぐ。
- コスト区分が用途で分かれる場合、区分は**内容変更のたびに再判定**する。
  **不明な場合は高いほうの単価で見積もる**
  （理由: 過小見積もりは請求超過という不可逆な結果を生む）。
```

## §12 に貼るハードルール（ロール構成を採る場合）

```markdown
### 12.3 Hard rules（ハーネス）

- 🔴 **ロールは自律エージェントではない**。入出力スキーマが定義されたパイプラインの工程である。
  ロールに「自分で何をするか決めさせる」設計を採らない
  （理由: コストと事故が制御不能になる）。
- **ロール間の受け渡しは構造化データ**で行う。自由文を次のロールに渡して解釈させない。
- **品質ゲート担当の拒否権を他ロールが迂回できない**。
- **各成果物に、生成したロール・使用プロンプト版・モデルを記録する**。
- 🔴 **利用量記録にロール識別子を必ず含める**。ロール別原価の分解はこれに依存するため、
  欠けていたら機能欠損と同義とする。
- **ロールごとにモデルを設定可能にする**。ハードコードしない
  （理由: ロール別のモデル使い分けが AI 原価の最大の調整弁になる）。
- **ロールの実行単位はジョブ**。失敗・再試行・タイムアウトの単位もロール単位とする。
```

### 12.4 ロール別の承認モード

```markdown
- **既定はすべて「都度承認」**。自動承認は明示的な opt-in でのみ有効になる。
- 🔴 **品質ゲート担当に承認モードは存在しない。設定項目自体を作ってはならない**
  （理由: §3.3 のゲートを迂回する経路になる）。
- **実行（公開・送信）の承認は本節の対象外**。§3.3 のハードルールのみが支配する。
- **承認モードの変更は監査ログに記録する**。
- **自動承認でも成果物は記録され、後から遡って確認・巻き戻しができる**こと。
```

## レビュー観点

- [ ] AI SDK の直接 import がラッパ以外に無いか（`Grep` + Lint 実行で確認）
- [ ] 許可されていない AI プロバイダが追加されていないか
- [ ] **全ての AI 呼び出しに利用量記録の経路があるか**（記録漏れは無条件 NG）
- [ ] 利用量記録に**ロール識別子**が含まれているか（§12 がある場合）
- [ ] LLM 出力のパースがスキーマ経由か。正規表現パースが無いか
- [ ] パース失敗・API エラーが握り潰されていないか
- [ ] プロンプトが所定のディレクトリにあり、ベタ書きされていないか
- [ ] 生成物に**プロンプト版・モデル・ロール**が記録されているか
- [ ] 外部由来テキストとシステム指示の境界があるか
- [ ] **ロールが自律エージェントとして実装されていないか**（次の行動をモデルに決めさせていないか）
- [ ] ロール間の受け渡しが構造化データか
- [ ] ロールのモデル指定がハードコードされていないか

## ユニットテストで押さえる点

- 利用量が記録されること（ラッパを通した呼び出しで記録行が増える）
- パース失敗時のフォールバックが仕様どおりであること（握り潰していないこと）
- ロール別のモデル設定が反映されること
