# recipe: 承認・品質ゲート

> 対応する章: `CLAUDE.md` §3.3 / §4.2
> 該当するプロダクト: 生成物やユーザー投入物に審査・承認が要る（特に AI 生成物を外部に出す場合）

## 守りたいこと

**承認されていないものが実行（公開・送信・発注）されないこと。**

AI が生成したものを外部に出すプロダクトでは、これが品質と信頼の最終防衛線になる。ゲートが 1 度でも迂回されると、**「このプロダクトはチェックが効いている」という前提そのものが崩れる**。

## 🔴 静かに壊れる経路

### 1. 承認後に内容を変更できてしまう

最も見落とされる穴。

```
生成 → 品質ゲート PASS → 人間が承認 → 内容を編集 → 実行
                                        ↑ ここで承認が無効になっているはず
```

編集の経路は 2 つあり、**両方塞ぐ必要がある**：
- **人が手で直す**（分かりやすい）
- **AI が再生成する**（見落としやすい。「再生成」は編集だと認識されにくい）

🔴 **内容が変更された成果物は、再検証を経ずに承認できない。** 変更を検知したら承認状態をリセットし、ゲートを再通過させる。

### 2. UI で隠しただけで、サーバ側は通してしまう

「未承認なら承認ボタンを出さない」は UI の話であって、**認可ではない**。API を直接叩けば通る。

🔴 **サーバ側で状態遷移を拒否する。** `InvalidStateTransitionError` (HTTP 422) を返す。UI 側の制御は「使いやすさ」のためであって、ゲートの実装ではない。

### 3. 自動モードがゲートを飲み込む

「全自動モード」を用意すると、実装がこうなりがち：

```
if (autoMode) { publish(); }   // ← ゲートを通っていない
```

正しくは：

```
if (autoMode && gateResult.allLayersPassed) {
  approve({ approver: 'system' });   // 承認は「与える」のであって「飛ばす」のではない
}
publishOnlyIfApproved();
```

🔴 **1 層でも FAIL したら、自動モードでも人間に差し戻す。** 自動モードは「承認を自動で与える」機能であって、「ゲートを無効化する」機能ではない。

### 4. ゲートの結果が承認画面に出ていない

ゲート自体は動いていても、**承認者がゲート結果を見ずに承認できる導線**があると、実質的に形骸化する。特にモバイル画面で「狭いから」と判断材料を省略すると起きる（`CLAUDE.md` §13.3）。

🔴 **承認画面には、成果物・ゲート結果・プレビューが 1 画面に収まっていること。**

### 5. 一括承認がゲート FAIL 分を巻き込む

「N 件まとめて承認」を実装するとき、**FAIL しているものが一括対象に混ざる**と、ゲートの意味が消える。一括対象からは FAIL 分を除外し、除外した件数を UI に明示する。

### 6. 品質ゲートに「承認モード」設定を作ってしまう

AI 運用ロール（`CLAUDE.md` §12）を採る場合、各ロールに「都度承認 / 自動承認」の設定を持たせることがある。このとき**品質ゲート担当のロールにも同じ設定を作ると、ゲートを設定で無効化できてしまう**。

🔴 **品質ゲート担当に承認モードは存在しない。設定項目自体を作ってはならない。**

## 設計の型

### ゲートを層に分ける

ゲートは 1 枚岩にせず、**性質の違う層**に分ける。層ごとに「誰が直すか」が変わるため。

| 層 | 例 | FAIL したときの対処 |
|---|---|---|
| 機械的検証 | 文字数・必須項目・禁止語・形式 | 自動修正または再生成 |
| ポリシー検証 | 外部サービスの規約・法令・社内基準 | 内容の作り直し |
| 品質評価 | 一貫性・トーン・訴求力 | 人間の判断 |

**層ごとに結果を記録する。** 「FAIL した」だけでは、誰が何を直せばよいか分からない。

### 状態遷移で担保する

```
生成済 ──[ゲート実行]──▶ ゲートFAIL ──[修正]──▶ 生成済 (再度ゲートへ)
   │
   │ [全層 PASS]
   ▼
ゲートPASS ──[承認]──▶ 承認済 ──[実行]──▶ 実行中 → 完了
   │                      │
   │                      └──[内容変更]──▶ 生成済 (承認リセット・再ゲート)
   └──[内容変更]──▶ 生成済
```

🔴 **`承認済` を経ずに `実行中` へ遷移する経路を、状態機械のレベルで存在させない。**

## §3.3 に貼るハードルール

```markdown
### 3.3 承認・品質ゲート

- {{対象}} は**必ず {{GATE_ENTITY}} を通す**。ゲートは {{層数}} 層: {{層の列挙}}。
  層ごとに結果を記録する（理由: 「FAIL した」だけでは誰が何を直すか判断できない）。
- 🔴 **`{{ENTITY}}` は `{{APPROVED_STATE}}` を経ずに `{{EXECUTING_STATE}}` に遷移してはならない**。
  この禁止は**サーバ側の状態遷移で担保する**。UI でボタンを隠すのは実装ではない
  （理由: API を直接叩けば通ってしまう）。不正遷移は `InvalidStateTransitionError` (HTTP 422)。
- 🔴 **内容が変更された成果物は、再検証を経ずに承認できない**。
  変更を検知したら承認状態をリセットし、ゲートを再通過させる。
  **AI による再生成も「変更」に含む**
  （理由: 再生成は編集として認識されにくく、承認後の差し替え経路になる）。
- 既定は**人間承認必須**。{{自動化フラグ}} が有効な場合に限り、**ゲート全層 PASS の場合のみ**
  承認を自動付与できる（承認者は `system` として記録し、監査ログに残す）。
  **1 層でも FAIL したら全自動モードでも人間に差し戻す**
  （理由: 自動モードは「承認を自動で与える」機能であり、「ゲートを無効化する」機能ではない）。
- **承認画面には、成果物・ゲート結果・プレビューを 1 画面に収める**。
  判断材料を見ずに承認できる導線を作らない（狭い画面でも同様。`CLAUDE.md` §13.3）
  （理由: 判断材料の無い承認は、ゲートの実質的な形骸化にあたる）。
- **一括承認の対象からゲート FAIL 分を除外し、除外件数を UI に明示する**。
```

## §12.4 を書く場合（AI 運用ロールがある場合）

```markdown
- 🔴 **品質ゲート担当に承認モードは存在しない。設定項目自体を作ってはならない**
  （理由: §3.3 のゲートを迂回する経路になる）。
- **実行（公開・送信）の承認は本節の対象外**。§3.3 のハードルールのみが支配する。
```

## レビュー観点

- [ ] 承認を経ずに実行状態へ遷移できる経路が無いか（状態機械の全遷移を列挙して確認）
- [ ] 🔴 **内容変更（AI 再生成を含む）で承認がリセットされるか**
- [ ] 🔴 **修正直後の承認要求が「サーバ側で」拒否されるか**（UI で隠すだけは NG）
- [ ] 自動承認の条件が「ゲート全層 PASS **かつ** 自動モード有効」になっているか
- [ ] 自動承認時の承認者が `system` として記録され、監査ログに残っているか
- [ ] 一括承認から FAIL 分が除外されているか
- [ ] 品質ゲートに承認モード設定が作られていないか（§12 がある場合）
- [ ] **ゲートのルールに対するユニットテストがあるか**（NG 判定が期待どおり出ること）

## E2E で必ず押さえるシナリオ

- 未承認の成果物が実行されないこと。閲覧のみのロールに承認 UI が出ないこと
- ルール違反の入力が FAIL となり、指摘が UI に表示され、**承認できない**こと
- 自動モード有効かつ全層 PASS で無人実行されること。**ゲート FAIL 時は自動モードでも人間に差し戻る**こと
- 承認後に内容を編集し、**再度ゲートを通さないと承認できない**こと
- モバイルビューポートで承認フローが完結し、**判断材料が承認前に確認できる**こと
