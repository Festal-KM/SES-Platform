# recipe: デモ環境・環境分離

> 対応する章: `CLAUDE.md` §11
> 該当するプロダクト: 本番・開発以外の環境（営業デモ / ステージング / トライアル）が要る

## 守りたいこと

**営業デモで機能を実演できること。そして、デモ操作が本番の外部サービスに一切影響しないこと。**

デモ環境は「本番のように動く」必要があるが、「本番と同じことをする」わけにはいかない。ここを曖昧にすると、**商談中に顧客のアカウントから実際に投稿が飛ぶ**ような事故が起きる。

## 🔴 まず「守るべき危険」を 1 行で特定する

危険の輪郭がぼやけたまま統制を書くと、**粗すぎて機能を殺すか、細かすぎて漏れるか**のどちらかになる。

まず 1 行で書く。例：

> 🔴 **営業デモの操作が、実在の外部サービスに書き込みを起こしてはならない。**

これが決まると、統制は自然に定まる：「デモ環境から外部書き込みコネクタが実装に到達しないこと」。逆に、読み取り系や AI 生成は実物を使ってよい（デモの説得力に直結するため）。

## 🔴 静かに壊れる経路

### 1. 「未設定ならモックにフォールバック」

最悪の壊れ方を生むパターン。

```javascript
const connector = process.env.API_KEY ? new RealConnector() : new MockConnector();
```

一見安全に見えるが、**本番で環境変数の設定を 1 つ忘れると、モックが選ばれる**。すると：

- アプリはエラーを出さない
- UI は「投稿完了」と表示する
- **実際には何も起きていない**
- 顧客は数日後に気づく

🔴 **`production` でモック実装が選ばれ得る経路を作らない。** 本番で外部連携の設定が欠けているなら、**起動時に失敗させる**のが正しい。「成功したように見えて実際には起きていない」は、明示的なクラッシュより遥かに高くつく。

### 2. 環境判定の `if` がコード中に散る

```javascript
if (process.env.APP_ENV !== 'production') { return mockResult; }   // ← あちこちに増える
```

分岐が増えると**必ず 1 箇所漏れる**。そして漏れた箇所が、本番でモックを返すか、デモで実 API を叩くかのどちらかになる。

🔴 **外部連携の差し替えは、起動時の 1 箇所（DI / ファクトリ）で行う。** リクエストごとの `if` 分岐を書かない。レビューでは `APP_ENV` の参照箇所を `Grep` で数え、**増えていたら NG** にする。

### 3. デモ用モックと E2E 用モックを別々に書く

同じ「外部 API のモック」を 2 つ書くと、片方だけ仕様が更新されて乖離する。すると **E2E は通るがデモでは壊れる**（またはその逆）。

🔴 **モック実装は 1 つにして、デモ環境と E2E テストで同じものを使う。**

### 4. 本番データをコピーしてデモ環境を作る

「リアルなデモにしたいから」と本番の顧客データをコピーすると：

- 顧客 A の商談で顧客 B のデータが画面に出る
- 個人情報の取り扱いとして契約違反になり得る

🔴 **本番の顧客データを他環境にコピーしない。合成データを使う。**

### 5. 今どの環境にいるか分からない

運営者もエンジニアも、同じ UI を複数環境で見る。**見た目が同じだと必ず取り違える**。

🔴 **本番でないことを UI に常時表示する**（最上部の帯など）。

## 設計の型

### 環境の定義

| 環境 | `APP_ENV` | 用途 | 外部 API |
|---|---|---|---|
| 開発 | `development` | ローカル開発・自動テスト | **モック** |
| デモ | `demo` | 営業デモ・トライアル | **書き込み系はモック / 読み取り・AI は実物** |
| ステージング | `staging` | リリース前検証 | **サンドボックス or モック** |
| 本番 | `production` | 顧客の実運用 | 実 |

**「外部 API をモックにするか」は一律ではなく、書き込み系と読み取り系で分ける**のが実務的。デモで AI 生成が実物なら説得力があり、かつ危険ではない。

### 差し替えは起動時の 1 箇所で

```
起動
 └─ createConnectorRegistry(APP_ENV)      ← ここだけが環境を知っている
      ├─ production  → RealWriteConnector
      ├─ demo        → MockWriteConnector + RealReadConnector
      └─ development → MockWriteConnector + MockReadConnector

アプリコードは registry から取るだけ。APP_ENV を知らない。
```

### 本番の設定欠落は起動時に落とす

```
production かつ 外部連携の設定が欠けている → 起動時に例外を投げてプロセスを終了する
```

フォールバックしない。**起動しないほうが安全。**

## §11 に貼るハードルール

```markdown
### 11.1 Hard rules（環境分離）

- 🔴 {{最も避けたい事故。例「営業デモの操作が実在の外部サービスに書き込みを起こすこと」}}。
  **設計で物理的に不可能にする**（運用の注意で担保しない）。
- **外部連携の差し替えは `APP_ENV` による起動時の 1 箇所（DI / ファクトリ）で行う**。
  リクエストごとの `if` 分岐にしない
  （理由: 分岐が増えると必ず 1 箇所漏れ、その 1 箇所が事故になる）。
  レビューでは `APP_ENV` の参照箇所数を確認し、増えていたら NG とする。
- 🔴 **`production` でモック実装が選ばれてはならない**。
  「未設定ならモックにフォールバック」を書かない。
  本番で外部連携の設定が欠けている場合は**起動時に失敗させる**
  （理由: フォールバックは「成功したように見えて実際には起きていない」という
   最悪の壊れ方を生む。明示的なクラッシュのほうが遥かに安い）。
- **モック実装は E2E テストのモックと同一実装を使う**。
  デモ用とテスト用に別々のモックを書かない（理由: 片方だけ更新されて必ず乖離する）。
- **本番の顧客データを他環境にコピーしない**。合成データとする。
- **シードデータは冪等に再生成できる**こと。
- **本番でないことを UI に常時表示する**（最上部の帯など）。
```

## §7 に貼る KPI

```markdown
| デモ環境からの実外部サービスへの書き込み | **0 件**（許容しない） |
```

## レビュー観点

- [ ] 外部連携の差し替えが**起動時 1 箇所**か。`APP_ENV` の参照箇所が増えていないか（`Grep` で数える）
- [ ] 🔴 **`production` でモック実装が選ばれ得る経路が無いか**（フォールバックは NG）
- [ ] 本番で外部連携の設定が欠けている場合、起動時に失敗するか
- [ ] モック実装が E2E のモックと**同一実装**か
- [ ] シードデータに本番顧客データ由来の値が混入していないか
- [ ] 環境表示バーが本番以外で常時表示されるか

## E2E で必ず押さえるシナリオ

- 非本番環境で外部書き込み操作を行い、**実 API が呼ばれず、モックが呼ばれる**こと
- 環境表示バーが表示されること（本番以外のビルド設定で）
