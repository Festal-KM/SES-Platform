# recipe: 外部書き込みの冪等性

> 対応する章: `CLAUDE.md` §3.4 / §4.2 / §7
> 該当するプロダクト: 取り消せない外部書き込み（SNS 投稿・メール送信・決済・API 経由の発注）がある

## 守りたいこと

**同じものを 2 回外部に出さないこと。**

内部の DB なら間違えても直せる。しかし外部に出したものは取り消せない。顧客のアカウントから同じ投稿が 2 回流れる、同じ請求が 2 回走る、同じメールが 2 回届く——**これらは「後で直す」ができない**。

`CLAUDE.md` §7 に `**0 件**（許容しない）` と書くべき項目。

## 🔴 静かに壊れる経路

### 1. ジョブキューのリトライが二重実行を作る

ほぼすべてのジョブキューは、失敗したジョブを自動リトライする。**これが最大の敵**になる。

外部 API を呼んだ直後にタイムアウトした場合：

```
外部 API 呼び出し → (実際には成功) → 応答待ちでタイムアウト → ジョブ失敗扱い
  → キューが自動リトライ → もう一度投稿される
```

🔴 **外部 API の結果が確定した後にリトライしてはならない。** 外部書き込みジョブの `max_attempts` は原則 `1` にする。「念のため 3 回」は事故の設定。

### 2. read-then-write のレースで 2 プロセスが同時に通る

```
プロセス A: 状態を読む → "予約済" → 送信してよいと判断
プロセス B: 状態を読む → "予約済" → 送信してよいと判断   ← A の更新前に読んだ
プロセス A: 状態を "実行中" に更新 → 送信
プロセス B: 状態を "実行中" に更新 → 送信              ← 二重投稿
```

単純な read-then-write は必ずこれを起こす。**条件付き UPDATE (CAS: compare-and-swap)** にする：

```sql
UPDATE jobs SET state = 'RUNNING', started_at = now()
WHERE id = $1 AND state = 'SCHEDULED'
RETURNING id;
```

**返る行数が 0 なら、他のプロセスが既に取っている。** その場合は何もせず終了する。

### 3. 🔴 事前判定を CAS の「後」に置いてしまう

これは実際に踏むまで気づかない罠。

送信直前には、たいてい複数の事前判定がある：
- 前提条件は満たされているか（連携が切れていないか）
- レート上限に達していないか
- コスト上限に達していないか

これを **CAS の後に置くと、抵触時にジョブが「実行中」状態のまま失敗する**。すると：

```
実行中 → 失敗 → この "失敗" は「送信前に止まった」のか「送信後に失敗した」のか区別できない
  → 復帰可否の条件分岐が必要になる
  → その分岐を 1 つ間違えると、送信済みのものを再送する
```

🔴 **事前判定は必ず CAS の「前」に置く。** 抵触したら**実行状態に入れず、保留状態へ遷移させる**。

```
[正しい順序]
1. 事前判定（前提条件・レート上限・コスト上限） → 抵触なら 保留 へ。ここで終了
2. CAS: 予約済 → 実行中                        → 0 行なら他が処理中。ここで終了
3. 外部 API 呼び出し
4. 結果を記録（成功 → 完了 / 明確な失敗 → 失敗 / 応答不明 → 隔離）
```

### 4. 「失敗」と「保留」を同じ状態にしてしまう

上と表裏一体。**外部要求の前に止まった**（保留）と、**外部要求の結果失敗した**（失敗）は**別の状態**にする。

混ぜると：
- 失敗率の指標が汚れ、監視が誤検知する
- 「自動復帰してよいもの」と「人間が判断すべきもの」が区別できなくなる

🔴 **保留は失敗ではない。** 原因が解消されたら自動で復帰する。失敗は復帰させない。

### 5. 応答不明を「未実行」と断定する

タイムアウトや 5xx で応答が不明なとき、「外部側を照会して、無ければ未送信だから再送する」という設計は**危険**。

- 外部サービスの反映に遅延がある
- 検索 API の索引が遅れている
- 応答は失われたが処理は成功している

🔴 **「実行されていた」は断定できるが、「実行されていなかった」は断定できない。**
応答不明のものは**隔離状態**に置き、**自動リトライを設定せず、人間の判断に委ねる**。

### 6. 冪等キーが「あるだけ」で効いていない

`idempotency_key` カラムを作っても、**`UNIQUE` 制約が無ければただのメモ**。

外部 API 側が冪等キーに対応していない場合、**CAS + `UNIQUE` 制約が唯一の防御線**になる。DB 制約で担保する。

## 設計の型

### 状態遷移

```
      ┌──────────────────────────────────────┐
      ▼                                      │ (原因解消で自動復帰)
  予約済 ──[事前判定 NG]──▶ 保留 ───────────┘
      │
      │ [事前判定 OK]
      ▼
  [CAS: 予約済 → 実行中]  ── 0 行 ──▶ 何もしない（他プロセスが処理中）
      │
      ▼
   実行中 ──── 外部 API ────┬── 成功 ────▶ 完了     (終端)
                            ├── 明確な失敗 ▶ 失敗     (終端 / 人間操作でのみ再実行)
                            └── 応答不明 ──▶ 隔離     (終端 / 自動リトライ禁止)
```

**片道の遷移**: `実行中` に入ったら、必ず `完了` / `失敗` / `隔離` のいずれかに確定させる。`実行中` のまま放置しない（滞留監視の対象にする）。

### レート制限とコスト上限は自前でガードする

外部 API の 429 に頼らない。理由：

- 429 が返る頃には**既に一部が送信済み**で、部分実行状態になる
- 従量課金の API では、429 に到達する前に**予算を使い切っている**
- 公称のレート上限と実測が食い違うことがある（**実測のほうが厳しい**）

アプリ層で「送信前に上限を確認し、抵触したら保留にする」ガードを置く。

  **DB の `UNIQUE` 制約で担保する**（外部 API 側に冪等性が無い場合、CAS + `UNIQUE` が唯一の防御線）。

  （「実行されていた」は断定できるが「されていなかった」は断定できない）。

  ログ・エラー・エラー追跡サービス・監査ログ・LLM プロンプトに絶対に出さない。

## レビュー観点

- [ ] `idempotency_key` が生成・保存され、**`UNIQUE` 制約が付いているか**
- [ ] 🔴 **事前判定が CAS の前にあるか**。抵触時に保留へ遷移しているか
- [ ] `予約済` → `実行中` が条件付き UPDATE になっているか（0 行時の分岐があるか）
- [ ] ジョブの `max_attempts` が `1` か。リトライ設定が入っていないか
- [ ] 応答不明時に隔離状態へ退避しているか。自動リトライが無いか
- [ ] 保留を「失敗」として扱っていないか。失敗率の指標に混ざっていないか
- [ ] 送信前のレート/コストガードがあるか。429 頼みになっていないか
- [ ] トークンがログ・エラー追跡・プロンプトに出ていないか（`Grep` で確認）
- [ ] **二重実行防止のユニットテストがあるか**（同一キーで 2 回実行し、外部モックの呼び出しが 1 回）

## E2E で必ず押さえるシナリオ

- 同一対象への実行処理を重複させ、**外部 API モックの呼び出し回数が 1 回だけ**であること
  （そのためにモックは呼び出し回数を記録できるようにしておく）
- レート/コスト上限到達時に実行が止まり、UI に警告が出ること
- トークン失効状態が UI に表示され、再連携導線が機能すること
