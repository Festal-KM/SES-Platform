# recipe: マルチテナントのデータ分離

> 対応する章: `CLAUDE.md` §3.1 / §10.5
> 該当するプロダクト: 複数の顧客組織のデータを 1 つの DB に格納する

## 守りたいこと

**あるテナントのユーザーが、他テナントのデータに 1 バイトも触れられないこと。**

SaaS でこれを破ると、他社の顧客名簿・売上・投稿内容が見えるという、**謝罪では終わらない事故**になる。`CLAUDE.md` §7 に `**0 件**（許容しない）` と書くべき筆頭項目。

## 🔴 静かに壊れる経路（ここが本題）

分離の恐ろしいところは、**壊れていてもアプリが正常に動く**ことにある。分離が無効になっても機能は動き、テストは通り、UI は正しく見える。**「テストが通っている」は分離が効いている根拠にならない。**

実際に踏んだ壊れ方：

### 1. ORM のクエリ傍受が raw クエリを素通りさせる

多くの ORM は「クエリを傍受してテナント条件を自動付与する」拡張機構を持つ。しかし **その傍受はモデル経由のアクセスにしか効かず、生 SQL 実行 API には効かない**ことがある。

結果として:
- モデル経由 (`db.post.findMany()`) → 正しくテナント条件が付く ✅
- 生 SQL (`db.$queryRaw` / `execute_sql` 相当) → **条件が付かず全テナントが返る** ❌

そして分析画面や集計ジョブは、たいてい生 SQL で書かれる。

🔴 **モデル経由のアクセスが正しく拒否されることは、分離が効いている根拠にならない。穴は raw にだけ開く。**

### 2. アプリの DB 接続ロールがテーブルの所有者になっている

PostgreSQL の行レベルセキュリティ (RLS) は、**テーブル所有者と `BYPASSRLS` 属性を持つロールには既定で適用されない**。マイグレーションを実行するロールと、アプリが接続するロールを分けていないと、**RLS を有効にしているのに全く効いていない**状態になる。

しかも、この状態でもアプリは完璧に動く。

### 3. コネクションプールでセッション変数が漏れる

RLS の条件を `SET LOCAL app.tenant_id = ...` のようなセッション変数で渡す設計の場合、**`LOCAL` を付け忘れるとトランザクション終了後も値が残り、プールで使い回された次のリクエストに漏れる**。

負荷が低いときは再現せず、同時接続が増えたときだけ他テナントのデータが混ざる。**最悪の再現性**を持つバグになる。

### 4. 分離キーをリクエスト入力から受け取る

`GET /api/posts?org_id=123` のように、**分離キーをクライアントから受け取る**設計にすると、値を書き換えるだけで他テナントのデータが取れる。テストは自テナントの ID しか送らないので通る。

分離キーは**必ず認証コンテキスト (セッション / JWT) から取る**。

## 設計の型

### 二重防御にする

| 層 | 手段 | 守るもの |
|---|---|---|
| アプリ層 | テナントスコープ付きアクセサ (`withTenant(ctx, ...)` 等) を唯一の DB 入口にする | 通常経路の事故 |
| DB 層 | 行レベルセキュリティ (RLS) | アプリ層をすり抜けた経路 |

**片方だけでは不十分。** アプリ層だけだと raw クエリで抜ける。DB 層だけだと、有効化漏れに気づけない。

### RLS を「実際に効かせる」ための前提条件

PostgreSQL で RLS を機能させるには、以下が**すべて**必要。1 つでも欠けると静かに無効化される。

1. テーブルに `ALTER TABLE t ENABLE ROW LEVEL SECURITY;`
2. `CREATE POLICY` でポリシーを定義（ポリシーが無い + RLS 有効 = 全行拒否になるので、これも忘れない）
3. **アプリの接続ロールがテーブル所有者ではない**こと
4. **アプリの接続ロールが `BYPASSRLS` を持たない**こと
5. （所有者にも適用したい場合）`ALTER TABLE t FORCE ROW LEVEL SECURITY;`

**この 5 条件を、マイグレーションのテストで機械的に検査する。** 新規テーブルが追加されるたびに人間が確認するのは必ず漏れる。

### 分離をバイパスする経路は 1 本だけにする

管理平面（`CLAUDE.md` §10）はテナント境界を越えて読む必要がある。このとき **`BYPASSRLS` を持つ専用の DB ロール**を用意するが、以下を守る：

- そのロールを使うクライアントは**専用モジュールに閉じ込める**
- **Lint の `no-restricted-imports` 相当でテナント平面からの import を禁止する**
- 🔴 **禁止が実際に効くことを、一時的な import を置いて Lint を走らせて確認する**。設定を書いただけで安心しない（パスのマッチが効いていないケースが実際にあった）

## §3 に貼るハードルール

```markdown
### 3.1 データ分離・アクセス境界

- 分離の単位は **{{TENANT_ENTITY}}**。分離キーは `{{TENANT_KEY}}`。
- DB アクセスは必ず `{{TENANT_SCOPED_ACCESSOR}}` 経由。**アプリ層のスコープ付きアクセサ**と
  **DB の行レベルセキュリティ (RLS)** の二重防御とする。片方だけに頼らない
  （理由: アプリ層だけでは生 SQL 経路が抜け、DB 層だけでは有効化漏れに気づけない）。
- `{{TENANT_KEY}}` は**必ず認証コンテキスト (ctx) から取得**する。リクエスト入力
  （クエリパラメータ・ボディ・ヘッダ）から受け取ってはならない
  （理由: 値の書き換えだけで他テナントのデータが取得できてしまう）。
- 🔴 **生 SQL を実行する API を、テナント平面のコードから直接呼ばない**。
  ORM のクエリ傍受はモデル経由のアクセスにしか効かず、**生 SQL には効かない**。
  やむを得ず使う場合は `{{RAW_QUERY_HELPER}}` を経由し、テナント条件を明示的に付与する。
- 🔴 **RLS をバイパスできる接続を持つクライアントは `{{ADMIN_DB_MODULE}}` に閉じ込め、
  Lint の import 制限でテナント平面からの参照を禁止する**。
  制限が効いていることは、設定の存在ではなく **Lint の実行結果**で確認する。
- 新規テーブルを追加するマイグレーションは、**RLS 有効化とポリシー定義を同一マイグレーションに含める**。
  分離が無効でもアプリは正常に動くため、**テストが通ることは分離が効いている根拠にならない**。
- **この規律の射程は {{射程: 例「テナントに属する業務テーブル全て」}} である。
  {{射程外: 例「認証テーブル・プラン定義などのグローバルマスタ」}} は含まない**
  （理由: {{理由}}）。**射程外にできるのはここだけ**であり、新たな例外を作ってはならない。
```

## レビュー観点（`code-reviewer` / `design-reviewer` が見る点）

- [ ] 全 DB 操作がスコープ付きアクセサを通っているか（`Grep` で DB クライアントの直接使用を数える）
- [ ] 分離キーが認証コンテキスト由来か。リクエスト入力由来の経路が無いか
- [ ] 🔴 **生 SQL で他テナントのデータを取りにいき、実際に拒否されることを確かめたか**
- [ ] 🔴 **バイパス用クライアントの import 制限を、Lint を実際に走らせて確認したか**
- [ ] 新規テーブルに RLS 有効化 + ポリシーがマイグレーションに同梱されているか
- [ ] アプリ接続ロールがテーブル所有者でないか、`BYPASSRLS` を持っていないか
- [ ] セッション変数を使う設計なら、`LOCAL` スコープになっているか

## E2E で必ず押さえるシナリオ

- 別テナントのリソース ID を URL に直接入力し、**サーバ側で 404 / 403 になる**こと
  （UI にリンクが出ないことは根拠にならない）
- 分析・集計など**生 SQL を使う画面**でも他テナントのデータが混ざらないこと
