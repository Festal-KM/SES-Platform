# recipe: 運営者コンソール（管理平面）

> 対応する章: `CLAUDE.md` §1.4 / §10
> 該当するプロダクト: SaaS として、自社スタッフが顧客テナントを管理・サポートする

## 守りたいこと

**運営者が仕事をできること。そして、運営者の権限が事故経路にならないこと。**

この 2 つは相反する。運営者はテナント境界を越えて見る必要があるが、それは §3.1 で作った分離を**唯一合法的に越える経路**でもある。だからこそ**最も慎重に設計する**。

## 🔴 なぜ「顧客の平面」と同じ重みで設計するのか

管理平面を後回しにすると、**運用できない製品ができあがる**。実際に起きること：

- 顧客から「動きません」と連絡が来ても、**運営者側から状態を見る手段が無い**
- 失敗したジョブが溜まっていることに**誰も気づかない**
- 従量課金の外部 API を再販している場合、**使えば使うほど赤字になるテナント**を検知できない
- 仕方なく本番 DB に直接クエリを打つ運用になり、**分離の設計が形骸化する**

🔴 **「本番 DB を直接触る運用」に落ちた時点で、§3.1 のハードルールは死ぬ。** 管理平面はその代替経路として設計する。

## 🔴 静かに壊れる経路

### 1. 運営者を「フラグ付きの一般ユーザー」にする

`User` テーブルに `is_admin` を足す設計は、**権限昇格の事故経路そのもの**。

- ユーザー編集 API に `is_admin` が渡ってしまう（Mass Assignment）
- テナント側のバグ 1 つで運営者権限が取れる
- 「運営者かどうか」の判定が、テナント側の認可コードに混ざって複雑になる

🔴 **運営者は `PlatformUser` として別テーブル・別認証にする。** テナントの `User` に運営者フラグを持たせない。

### 2. 分離バイパスが「汎用のエスケープハッチ」になる

管理平面のために `BYPASSRLS` を持つ DB クライアントを用意する。ここまでは必要。

問題は、それが**便利なので他の場所からも使われ始める**こと。「バッチ処理で全テナント見たいから」「集計が遅いから」——理由はいくらでも湧いてくる。

🔴 **バイパス用クライアントは専用モジュールに閉じ込め、Lint の import 制限でテナント平面からの参照を禁止する。** 制限が効いていることは、設定の存在ではなく **Lint の実行結果**で確認する。

### 3. 代理閲覧（impersonation）で書き込めてしまう

サポートのために「顧客の画面を代理で見る」機能は有用だが、**そのまま操作までできると、顧客のデータを運営者が勝手に変更できる**。しかも監査上、それが顧客自身の操作と区別できない。

🔴 **代理閲覧は read-only。代理状態での実行系操作は不可。**

### 4. 運営者コンソールが「書ける」ようになっていく

「サポートで直してあげたいから」という善意で、運営者がテナントの業務データを編集できる経路が増える。すると：

- 顧客のデータが「誰かが直したらしい」状態になる
- 障害の切り分けができなくなる
- 責任の所在が消える

🔴 **運営者コンソールは既定 read-only。** 書き込みが許されるのは**契約・クォータ・機能フラグ・お知らせ**に限る。

### 5. 運営者に見せてはいけないものが見えている

運営者は「全部見られる」わけではない。以下は**運営者にも見せない**：

- 外部サービスのアクセストークン平文
- 顧客のエンドユーザーの個人情報

前者は漏洩したら顧客のアカウントが乗っ取られる。後者は顧客が預かっているデータであり、SaaS 提供者が見てよい理由がない。

### 6. 認可がテナント側ミドルウェアに相乗りしている

`/admin` の認可をテナント側のミドルウェアで済ませると、テナント側の認可を変更したときに管理平面の認可も一緒に変わる。**別ルート・別ミドルウェアで独立させる。**

## 設計の型

### ロール階層

| スコープ | ロール | 権限 |
|---|---|---|
| Platform | `PLATFORM_OWNER` | 全権 |
| Platform | `PLATFORM_SUPPORT` | 監視・調査・サポート。**課金設定とテナント停止は不可** |
| Tenant | `OWNER` | 組織の全権。契約者・支払者 |
| Tenant | `ADMIN` | メンバー管理・設定変更 |
| Tenant | `EDITOR` | 業務データの作成・編集・承認 |
| Tenant | `VIEWER` | 閲覧のみ。**承認・実行の操作は一切不可** |

**Platform と Tenant は別の軸**。同じ列挙型に混ぜない。

### 運営平面の筆頭機能を 1 つ特定する

管理平面の機能は際限なく増やせる。**「これが無いと事業が回らない」機能を 1 つ特定して先に作る。**

従量課金の外部 API を原価として再販する構造なら、多くの場合それは **テナント別の原価と粗利の可視化**になる。受け入れ基準はこう書く：

> **使えば使うほど赤字になるテナントを検知できること。**

### 代理閲覧の 5 条件

代理閲覧は、以下を**すべて**満たす場合のみ許可する：

1. **理由の入力必須**
2. **時間制限付き**（残り時間を UI に常時表示）
3. **read-only**（実行系操作は不可）
4. **`ImpersonationSession` と `AuditLog` に記録**（誰が・いつ・どの組織を・何の理由で・何分間）
5. **対象組織の管理者に通知**

5 のない実装は「こっそり見られる」ことになる。信頼を売る SaaS では致命的。

### UI で 2 つの平面を取り違えさせない

運営者は両方の平面を見る。**一目で区別できないと、顧客のつもりで運営操作をする（またはその逆）事故**が起きる。

- ヘッダを反転色にする（テナント平面が白なら管理平面は黒）
- **ナビゲーションの形を変える**（テナント平面が左サイドバーなら、管理平面は水平タブ）
- 代理閲覧中は全幅バナーを常時表示

## §10 に貼る Hard rules

```markdown
### 10.5 Hard rules（管理平面）

管理平面はデータ分離を越える唯一の経路であり、最も慎重に設計する。

- 🔴 **運営者は別テーブル・別認証**（`PlatformUser`）。テナントの `User` に「運営者フラグ」を
  持たせる設計を採らない（理由: Mass Assignment とテナント側のバグが、そのまま権限昇格経路になる）。
- 🔴 **運営者コンソールは既定 read-only**。テナントの業務データを運営者が書き換えられる経路を
  作らない。書き込みが許されるのは**契約・クォータ・機能フラグ・お知らせ**に限る
  （理由: 顧客データが「誰かが直したらしい」状態になると、障害の切り分けと責任の所在が消える）。
- 🔴 **代理閲覧 (impersonation) は次をすべて満たす場合のみ**:
  ①理由の入力必須 ②時間制限付き ③**read-only** ④`ImpersonationSession` と `AuditLog` に記録
  ⑤対象組織の管理者に通知。**代理状態での実行系操作は不可**。
- 🔴 **分離のバイパスは専用の DB ロール経由に限定**し、専用モジュールに閉じ込める。
  **Lint の import 制限でテナント平面からの参照を禁止し、制限が効くことを Lint の実行で確認する**。
  汎用のエスケープハッチを作らない（理由: 便利なので必ず他所から使われ始める）。
- **管理平面は別ルート (`/admin`) かつ別ミドルウェアで認可**する。
  テナント側ミドルウェアに相乗りさせない。
- 🔴 **運営者にも見せないもの**: 外部サービスのアクセストークン平文、顧客のエンドユーザー個人情報。
- 運営者の全操作（**閲覧を含む**）を `AuditLog` に記録する。
- **UI 上、テナント平面と管理平面を一目で区別できること**（ヘッダの反転、ナビ形状の差異）。
```

## §10.6 Phase 配置

```markdown
| Phase | 管理平面のスコープ |
|---|---|
| **Phase 0** | `PlatformUser` の認証基盤と `/admin` ルートの分離だけ作る |
| **Phase 1** | テナント一覧・詳細、失敗ジョブの確認。
  🔴 **利用量の計測だけは Phase 1 から必ず行う**（後から遡って計測できないため） |
| **Phase 2** | 原価・粗利の可視化、クォータ管理、代理閲覧 |
```

🔴 **「利用量の計測は Phase 1 から」は妥協しない。** 画面は後で作れるが、計測されなかった過去は永遠に復元できない。

## レビュー観点

- [ ] 運営者が `PlatformUser` として別テーブル・別認証か（`User` への運営者フラグ追加は**無条件 NG**）
- [ ] 運営者経路からテナントの業務データへの書き込みが無いか
- [ ] 分離を素通りする汎用エスケープハッチが追加されていないか（`Grep` で DB クライアント直接使用を確認）
- [ ] 代理閲覧中の実行系操作が**サーバ側で**拒否されているか（UI 非表示のみは NG）
- [ ] `ImpersonationSession` / `AuditLog` への記録があるか
- [ ] 運営者向け応答でトークン平文・PII がマスキングされているか
- [ ] `/admin` の認可がテナント側ミドルウェアに相乗りしていないか
- [ ] 外部呼び出し・AI 呼び出しが利用量計測に計上されているか（**計上漏れは無条件 NG**）

## E2E で必ず押さえるシナリオ

- 運営者アカウントで、テナントの業務データを書き換える操作が**サーバ側で拒否される**こと
- 代理閲覧中に実行系操作ができないこと。バナーが常時表示されること。記録が残ること
- 権限の低い運営者ロールが、禁止された操作を実行できないこと
- 運営者コンソールの応答にトークン平文・PII が含まれないこと
- 実行・AI 呼び出し後に利用量が加算され、運営者コンソールに反映されること
